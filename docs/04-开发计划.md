# 御书 · 开发计划
> **一句话定位：御书把「从起源构建世界」拆成 M0→M6 七个可验收阶段，每阶段用「目标 / 前置依赖 / 任务 / 产物 / 验收标准 / 风险 / 退出条件」七要素锁死边界，以 M1 最小验收场景作第一条铁门槛，逐阶段把世界引擎、记忆系统、一致性引擎与本地数据主权交付到作者手上。**
>
> 文档版本：M0 规划期 ｜ 上游：docs/03-开发规划方案、docs/01-需求总纲 ｜ 下游：M1 启动

本文档承接 docs/00-交接文档 §6.3 的硬性要求：把开发拆成可执行阶段，每阶段提供七要素，并原样保留 M1 最小验收场景。技术边界一律以 docs/03 为准（分层架构、包依赖方向、五条工程红线），功能范围一律以 docs/01 为准（§4 MoSCoW、§5 非目标、§7 验收基线）。术语与 docs/01、docs/03 完全一致：**派系包、世界引擎、流派引擎、记忆系统、一致性引擎、起源工作台、作者刚需套件**。引用调研结论只用编号（K15、J03、I09 等），不引外部链接。

## 1. 计划总则
### 1.1 编排原则
1. **架构边界先行**：任何阶段的实现都不得越过 docs/03 §2–§4 的分层与包依赖方向（`apps → 引擎包 → @yushu/core`），不得让 AI 逻辑渗回内核。
2. **数据主权可验证**：每个阶段的验收里都必须有一条「删除 SQLite 索引后全量重建、零数据丢失」的实测，而不是口头承诺（docs/01 §6）。
3. **本地功能先于 AI**：AI 副驾永远最后一个接入，且必须能整体关闭而本地能力完整（docs/01 §7 验收基线）。
4. **退出条件收口，而非日历收口**：§2.1 的工期只是相对参考；七要素中的「退出条件」不满足，不得进入下一阶段。
5. **阶段不可越级、子项可裁剪**：M4–M6 内部子项允许延后到后续小版本，但七要素、退出条件与 DoD 不可跳过。
6. **不做超出范围的事**：随时对照 docs/01 §5 非目标，v1 不做多人实时协作、不做移动端、不强制云端账号（见 §12）。
### 1.2 上游锚点：Must 项与阶段的映射
docs/01 §4 的 Must 项必须全部落在 M1–M3：

| docs/01 §4 模块 | 落地阶段 | 说明 |
|---|---|---|
| §4.1 起源工作台【Must】 | **M1** | 引导式问卷 + 结构化设定卡 + 命名生成器（最小可用版） |
| §4.2 世界引擎【Must】 | **M1** 基座 → **M4** 深化 | M1 交付分层模型与依赖图；M4 交付影响传播、编年史、时间线校验 |
| §4.3 记忆系统【Must】 | **M2** → **M3** | M2 交付事实级记忆与索引；M3 交付五层记忆与上下文组装 |
| §4.4 大纲系统【Must】 | **M1** | 总纲→卷纲→章纲三级骨架 + 流派大纲模板 + 双向映射 |
| §4.5 AI 副驾【Must】 | **M3** | Provider 抽象、能力矩阵、任务路由、候选 diff、成本面板 |
| §4.6 作者刚需套件【Must】 | **M1**（导出/敏感词）→ **M2**（统计/快照/崩溃恢复） | 防丢稿四层防线在 M2 收口 |
| §4.7 编辑器【Must】 | **M1**（基础）→ **M2**（稳定化） | TipTap + CodeMirror 6 双形态在 M2 达到可日更标准 |
| §4.8–§4.10 Should / Could | M5 / M6 | 出版管线、可视化、插件与社区，见对应阶段 |
### 1.3 全阶段定义完成（DoD）
- **代码**：lint / typecheck / 单测通过；`perf-budget.yaml`（docs/03 §14）无退化；无新增高危安全反模式。
- **数据**：任何格式变更带 `schema_version` + 幂等迁移脚本 + 迁移前自动备份 + 可回滚（docs/03 §15）。
- **文档**：`CHANGELOG.md` 的 `Unreleased` 段有记录；重大决策落 `docs/adr/`；用户可见功能写帮助页。
- **证据**：本阶段验收场景可复现（脚本或 checklist），失败项必须开 issue 并登记到风险登记册（§10）。

### 2.2 跨阶段关键路径
```mermaid
flowchart LR
  M0["M0 规划与研究归档"] --> M1["M1 世界基座 MVP"]
  M1 --> M2["M2 编辑器与本地数据层"]
  M2 --> M3["M3 AI Provider 与记忆"]
  M3 --> M4["M4 一致性/伏笔/时间线/图谱"]
  M4 --> M5["M5 地图/工坊/导入导出"]

  M1 -. "真源↔索引契约（docs/03 §6）" .-> M2
  M2 -. "索引重建 + 事实级记忆" .-> M3
  M2 -. "章节实体状态机" .-> M4
  M3 -. "上下文组装与别名触发" .-> M4
  M3 -. "Provider 抽象" .-> M6
  M4 -. "规则 DSL 求值层" .-> M5
  M5 -. "包格式版本化经验" .-> M6
```

**关键路径依赖说明（硬依赖）**：

1. **记忆系统（M3）依赖 M2 的索引重建能力**：分层记忆的事实级层要能定位到 `chapter_id + 字符区间 + hash`，而这是 M2 的 `chunks` / `file_index` 与 `rebuild` 才提供的（docs/03 §6、§10）。
2. **一致性引擎（M4）依赖 M2 的章节实体状态机与 M3 的设定注入**：校验比对源是设定库 + 带出处的事实级记忆，没有 M2/M3 就只有空壳规则。
3. **影响传播（M4）依赖 M1 的依赖图与 M2 的 `refs` 反向索引**：docs/03 §7 的传播算法建立在 `refs` 表之上。
4. **派系包工坊（M5）依赖 M4 的规则 DSL 求值沙箱**：工坊必须能即时 lint 用户新建的规则，否则无法「导出前自检」。
5. **插件 API（M6）依赖 M3 的 Provider 抽象与扩展点注册中心**：插件可申请 `ai_task` 权限，必须复用同一 Provider 通道与证据链。
### 2.3 阶段内任务依赖约定
- 阶段内任务以编号 `T<阶段>-<序号>` 标识，依赖关系在任务清单里用 `（依赖 T1-3）` 显式标注。
- 允许并行：同一阶段内无依赖标注的任务可并行推进；被依赖项未完成时，下游任务只能做脚手架，不得提交假实现。
- 每阶段结束前必须重新运行上一阶段的全部验收脚本，防止回归（「阶段门禁不推翻上一阶段门禁」）。

## 11. 开源运营
本节以 **K15-开源运营与社区** 为直接输入，落实 docs/01 §4.10 的社区运营要求。
### 11.1 许可证选择建议
| 对象 | 建议许可 | 理由与边界 |
|---|---|---|
| **内核代码**（`apps/` + `packages/`） | **Apache-2.0** | 宽松 + 显式专利授权 + 州变更声明，适合桌面分发并允许与商业插件共存；备选 MIT（最短宽松，但无专利条款） |
| **派系包内容**（官方示例包） | **CC-BY-4.0**（默认，与 docs/03 §5.4 示例一致）；需要「同许可分享」的包可用 CC-BY-SA-4.0 | 内容与代码许可分离；包作者可自选并在 manifest `metadata.license` 声明 |
| **示例素材 / 品牌** | 素材单独声明；**品牌与官方分发受商标约束** | 允许闭源分叉代码，但不允许冒用「御书」名义分发（K15 折中方案） |

**明确不选强 copyleft（GPL/AGPL）作为内核**：会引发「派系包与插件是否衍生作品」的争议，吓退商业插件作者（K15 §2.1）。文档须同时声明「派系包为数据、插件通过稳定 API 交互」以降低衍生争议。仓库需 `LICENSE` + `NOTICE`（第三方依赖与再分发声明）+ 内容许可三份分离文件。
### 11.2 贡献流程与贡献者授权
- **DCO 而非 CLA**：贡献者 `git commit -s` 附加 `Signed-off-by`；CI 内置 `dco-check` 拦截缺失签署（K15 §3.2）。未来若需双许可再叠加 CLA。
- **四份社区健康文件齐备**：`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`（Contributor Covenant 2.1 中文版 + 举报邮箱 + 督促→警告→临时封禁→永久开除四级阶梯）、`SECURITY.md`（漏洞渠道、披露时限、支持版本范围）、`GOVERNANCE.md`。
- **issue/PR 模板**：YAML 表单（含行为准则勾选项）+ `config.yml`；PR 模板强制「关联 issue + 验证说明」；模板含 `pack-submission.yml`。
- **中文一等公民**：文档双语（中文为默认 + 英文镜像）、GitHub 与 Gitee 双镜像、Discussions 与国内社群并行；贡献指南给出「轻量级 PR」与 issue 认领话术（K15 §2.8）。
- **标签体系**：`good first issue`、`help wanted`、`type/*`、`area/*`（editor / world-engine / memory / pack-toolchain）、`status/*`。
### 11.3 发布节奏与版本规范
- **SemVer 2.0.0**：不兼容变更升主版本、向下兼容新增升次版本、修复升修订号；`0.y.z` 明确标注为初始开发期、API 不稳定。引擎、派系包、插件**各自独立 SemVer**，包用 `requires.yushu` 声明可运行区间（G06）。
- **CHANGELOG（Keep a Changelog）**：仓库维护 `CHANGELOG.md`，顶部保留 `Unreleased`，日期用 ISO 8601，条目归入 Added / Changed / Deprecated / Removed / Fixed / Security 六类（不得新增第七类）；**可省功能公告，不可省弃用、移除与破坏性变更**；禁止 dump commit log。
- **发布节奏**：M1–M5 阶段末各打一个 minor/major-after-0 版本 tag（`v0.1.0-alpha` → `v0.2.0` → `v0.4.0` → `v0.5.0` → `v0.7.0`），M6 发 `v1.0.0`；预发布用 `-alpha.N` / `-rc.N`；被撤回版本标 `[YANKED]`。
- **辅助校验规则**（CI）：`oss-license-presence`、`oss-dco-signoff`、`oss-changelog-format`、`oss-semver-bump`、`oss-breaking-undocumented`、`pack-id-namespace`、`pack-eleven-piece`（K15 §5）。
### 11.4 社区治理：RFC 与 ADR
- **RFC 流程**（参照 Rust 范式）：重大设计（存储格式、扩展点、规则 DSL、插件 API 核心面）先提 `docs/rfc/NNNN-*.md`，公开讨论权衡，进入「最终评论期」后才采纳。
- **ADR 决策日志**：`docs/adr/NNNN-*.md`，字段含「背景与问题 / 考虑过的方案及利弊 / 决定 / 后果 / 状态（Proposed→Accepted→Deprecated→Superseded）」；新决定取代旧决定时更新 `Superseded by`。本文档 §4.5 的误报阈值、§9.3 的插件 API 冻结面均须落 ADR。
- **维护者梯队与 owner**：`GOVERNANCE.md` 定义「贡献者 → 复审者 → 维护者 → 核心团队」路径；`CODEOWNERS` 按领域（editor / world-engine / memory / pack-toolchain）指派复审者。
- **独立 moderation**：行为准则执行与冲突调解由独立角色承担，与代码维护者分离。
- **商业化边界承诺**：写入 `GOVERNANCE.md` 与 README——核心离线能力永久免费；商业化只做可选服务（云备份、托管派系包目录、企业支持），不牺牲数据主权（docs/01 §5 非目标）。
### 11.5 派系包社区分享规范
提交工坊/目录前必须通过 lint 并产出符合 `submission` schema 的 YAML（K15 §5）：

- **命名空间**：`id` 全局唯一并作命名空间前缀，与既有包冲突即 error。
- **版本与兼容**：SemVer + `requires.yushu` 区间；破坏性变更升主版本并附迁移脚本。
- **11 件套齐全性**：world_preset / schema_extensions / rules / beat_sheets / satisfaction_patterns / prompt_templates / glossary / taboos / outline_templates / evolution / platform_mapping（对齐 docs/01 §3.2 与 G06）。
- **权限声明**：插件声明 `filesystem | network | ai_task | editor_write`；使用未声明能力即 error。
- **安全与分级**：`contains_ai_prompts`、`network_required`、`content_rating: general | mature`；派系包内提示词模板不得绕过「AI 输出必须可标识、可审计」的约束。
- **内容出处**：必须填写 `sources`，术语/规则不得抄袭未授权材料。
- **审核状态**：`pending | approved | rejected` + 评分；结果回执到工坊。
### 11.6 「何时宣布开源」与「何时发布 v1.0」门槛
**宣布开源门槛（建议在 M1 完成后开启公开仓库）**：

## 12. 非目标与范围守则
与 docs/01 §5 严格一致，全阶段不得越界：

1. **不做云端账号强制体系**：云备份是可选项，可选云备份 ≠ 云端身份；无强制登录、无账号门禁。
2. **v1 不做多人实时协作**：远期评估 CRDT；当前只做「文档为可序列化纯数据 + 修改走事务 + 节点稳定 id」的预留（docs/03 §15），不实现协同编辑。
3. **不做移动端**：v1 只做桌面端；存储格式为跨端预留，但不交付移动客户端。
4. **不内置模型训练，不做通用聊天助手**：AI 限定创作辅助场景，聊天入口不得扩展为通用对话产品。
5. **不替代平台发布流程**：只做格式适配与自查，不做投稿代理或平台账号集成。

范围守则补充：出现与上述冲突的新需求时，先提 RFC 修订 docs/01，**不得在实现层私自扩张范围**。
