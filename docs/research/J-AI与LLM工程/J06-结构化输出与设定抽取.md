# J06-结构化输出与设定抽取

> 类别：J-AI与LLM工程 ｜ 世界构建金字塔层级：工程层 · AI 工程
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究 LLM 输出"可机器校验的结构化内容"的工程方法，以及从自由文本中自动抽取结构化设定候选（人物/地点/势力/物品/功法技能/事件，见 docs/01 §4.3）的完整链路。边界划分：本领域管"输出契约"——即产出如何被约束成语义合法且 schema 合法的 JSON、抽取物如何从正文变成候选卡、候选如何在不违反数据主权原则的前提下入库；不研究设定本身怎么设计（A/B/C/D/E 类），也不研究注入侧（J03 上下文组装）。与 J07 分工：本领域保障"结构对不对"，J07 保障"内容对不对"。核心工程问题：如何让 AI 抽取可靠、可溯源，且永不直接改写真源（docs/01 §6 数据主权承诺）。

## 2. 核心知识框架

1. **结构化输出的三条路线**。（a）**Prompt 约束**：在提示词里要求输出 JSON，靠指令与 few-shot 示例，最脆弱，靠 J02 写作 Prompt 工程兜底；（b）**Function Calling / Tool use**：把目标结构声明为工具的 `input_schema`，模型返回 `tool_use`/`tool_calls` 块，由应用执行——Anthropic 明确其"客户端工具"往返流程，OpenAI 兼容系普遍支持；（c）**JSON Mode 与 JSON Schema 强约束**：JSON mode 只保证"是合法 JSON"，structured outputs 用 `json_schema` + `strict` 才保证"严格符合 schema"（类型、必填、枚举、`additionalProperties:false`）。Anthropic 以 `output_config.format`（JSON outputs）与 `strict:true`（strict tool use）两个互补特性实现，底层是语法约束解码（grammar-constrained sampling）。
2. **JSON Schema 作为唯一契约**。2020-12 规范分 Core 与 Validation 两部分，用 `$defs`/`enum`/`required`/`additionalProperties` 表达约束。御书把它同时用作"抽取任务定义"与"设定卡 schema"的共同语言，从而与 G06 的 schema 扩展点天然对齐。
3. **校验-重试闭环**。Instructor 模式：把 schema 写成 Pydantic 模型，校验失败时把**错误信息回喂**模型重试（有 `max_retries` 上限），形成"抽取→校验→修复→再审"的循环；错误应区分语法错误、类型错误、业务语义错误三类。
4. **抽取任务的类型学**。实体抽取（六类核心实体）、关系抽取（人物关系/势力归属）、事实抽取（原子事实，FActScore 范式）、事件抽取（时间+参与者+结果）。抽取通常分两级：先抽"句子级原子事实"，再聚合为"实体卡"。
5. **出处即契约**。每条抽取结论必须挂"回原文的 span 指针"（掘金 huadian 复盘契约：Source→Unit→Span 三层语料结构，粒度可调但指针不可缺）。
6. **成本分层**。抽取是高频低难任务 → 用便宜模型与 Batch 半价通道；正文生成才用旗舰（docs/01 §4.5 任务路由，J09）。

## 3. 可转化为产品规则的关键实践

1. 三路线自动降级 → Provider 能力矩阵声明 `structured_output`/`tools`；不支持 `json_schema` 时降到 JSON mode + 客户端校验，再降到提示词约束（J01/J09）。
2. 抽取任务 = JSON Schema 文件 → 每类实体一份抽取 schema，`extends` G06 的 `core/setting-card`，字段按项目启用的派系包动态拼装。
3. 校验失败自动重试 → 默认上限 2 次，把校验错误 diff 回喂模型；仍失败则落"抽取失败池"交人工处理。
4. 抽取结果不直接入库 → 一律写候选区（staging），走"候选→用户确认→入设定库"，AI 不得直接覆盖真源（docs/01 §6；G06 的 patch 分层思想）。
5. 候选必带出处 → 每条候选携带 `chapter_id + char span + quoted_text`，与 J13 证据链共用同一指针格式。
6. 冲突三分类 → 候选与既有设定卡比对，输出"新增/补充/冲突"三类（呼应 G06 融合预演报告）。
7. 抽取粒度控制 → 按章/按节切片抽取，长文先出节级中间结果再聚合，避免单次超上下文。
8. 便宜模型抽取 + 旗舰复核 → 抽取走便宜档，冲突或低置信候选可选旗舰模型复核（成本分层）。
9. 命名消歧 → 别名字典匹配 + 相似度合并建议，避免同一人物生成多张卡（Novelcrafter Aliases 思路）。
10. 排除词/负例表 → 抽取时排除"他/她/公司"等通名误抽，降低噪声（Novelcrafter exclusion 思路）。

## 5. 对御书设计的启示

**数据结构建议：抽取任务定义（由启用派系包动态拼装）**

```yaml
# schemas/extract-task.yaml
apiVersion: yushu.extract/v1
task: entity_extraction
target: [character, location, faction, item, skill, event]   # docs/01 §4.3 六类
model_tier: cheap          # 抽取默认便宜档（J09 任务路由）
capability: [structured_output, tools]   # 不支持时按序降级（J01）
input: {scope: chapter, slice_tokens: 1200}
output_schema:
  $ref: core/candidate-card              # 继承 G06 core/setting-card
  fields: [name, type, aliases, summary, source_span, confidence, evidence_refs]
retry: {max: 2, feed_back_error: true}   # 失败回喂错误再试
staging: candidates/                      # 只写候选区，不碰 settings/
disambiguation: {use_alias_dict: true, merge_threshold: 0.86}
```

**数据结构建议：候选卡（staging 产物，用户确认后才入设定库）**

```yaml
# candidates/ch-012.candidates.yaml
- candidate_id: cand-0007
  type: character
  name: 林渊
  aliases: [林公子, 渊儿]
  summary: 夜探藏经阁者，身怀残缺玉佩
  source_span: {chapter: ch-012, start: 842, end: 880, quote: "林渊抬手推开了藏经阁的木门"}
  evidence_refs: [ch-012]        # 与 J13 证据链共用指针
  confidence: 0.82
  diff_vs_existing: new          # new | augment | conflict
  status: pending                # pending | accepted | rejected（确认后回库）
```

**校验规则建议**

- `extract-schema-invalid`：抽取输出不符合 schema → error，并触发重试。
- `extract-retry-exhausted`：重试上限用尽仍不合规 → warn，落人工处理池。
- `extract-no-provenance`：候选缺 `source_span` → error（禁止无出处入库）。
- `extract-conflict-unconfirmed`：`diff_vs_existing=conflict` 却未经用户确认即写库 → error（AI 不得直接覆盖）。
- `extract-unknown-field`：出现项目未启用 schema 的字段 → warn（脏字段，可能来自他派系包）。

**功能建议**

- 抽取向导：选中章节 → 预览候选卡列表（按类型分组）→ 批量接受/逐条编辑/拒绝，冲突项单独高亮。
- 冲突对比视图：候选 A 与既有设定卡 B 并排 diff（字段级），提供"接受候选/保留原卡/合并"三选。
- 抽取失败池与日志：记录失败原因、原始返回、重试次数，便于排查 Provider 兼容性问题（J01）。

**AI 提示词建议**

- 抽取提示词：随附目标 JSON Schema 与本章正文，要求"只输出 JSON、不解释、无出处的结论不要输出、不确定的字段留空"。
- 修复提示词：把校验器返回的 schema 错误摘要回喂，要求"仅修正违规字段，其余字段保持原样"。
- 消歧提示词：输入候选 A 与既有卡 B 的名称/别名/摘要，输出 `{same: bool, reason}`，供合并建议参考。
