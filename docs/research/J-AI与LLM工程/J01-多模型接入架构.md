# J01-多模型接入架构

> 类别：J-AI与LLM工程 ｜ 世界构建金字塔层级：工程层 · AI 工程
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究御书如何用一套稳定抽象同时驱动云端旗舰、国产兼容模型与本地推理端点：Provider 描述与统一接口（chat/stream/embeddings/usage）、能力矩阵与自动降级、协议主干与原生适配、可靠性（重试/冷却/fallback/限流/并发）、任务路由与 API Key 本地安全。上游需求见 docs/01 §4.5（多模型接入=OpenAI 兼容主干 + Provider 能力矩阵 + Anthropic/Gemini 原生适配 + Ollama/llama.cpp/LM Studio 本地模型；任务路由；失败重试与 fallback 链）与 §6（API Key 与配置本地加密、AI 默认关闭可审计）。边界：J02 管"发什么提示词"，J09 管"花了多少钱"，J03 管"注入哪些记忆"；本领域只回答一个问题——请求如何抵达模型、失败如何自愈、密钥如何不出本机。

## 2. 核心知识框架

1. **OpenAI Chat Completions 是事实标准**。DeepSeek、智谱 GLM、阿里百炼、Kimi、MiniMax、阶跃、Ollama、llama.cpp、vLLM、LM Studio 均以 `/v1/chat/completions` 兼容 OpenAI：换 `base_url` 即用同一 OpenAI SDK。故御书以 OpenAI Chat Completions 为协议主干，只对 Anthropic Messages 与 Gemini generateContent 做原生适配层。
2. **Provider 抽象与统一接口**。参考 LiteLLM 的做法：任意 Provider 暴露同一函数签名，把 100+ Provider 差异收敛为参数与描述文件。御书统一接口取最小面 `chat / stream / embeddings / usage` 四个动词，其余字段差异由 Provider 描述文件声明。
3. **"兼容 ≠ 一致"——能力矩阵**。同一 OpenAI 协议下各家支持度不同（Ollama 不支持 `tool_choice`/`logit_bias`/`n`；vLLM 早期不支持 `tools`/`tool_choice`），必须由每个模型显式声明 `capabilities{tools, structured_output, stream, usage, reasoning, vision, cache, batch}`，请求前校验、不满足则降级而非报错。
4. **可靠性工程**。直连 Provider 会遇到 429/5xx/超时：需要固定+指数退避重试、失败计数触发冷却（LiteLLM 的 `allowed_fails`/`cooldown_time`）、按错误类型分级 fallback（限流 / 上下文超限 / 内容策略各有专用链）、并发上限与 RPM/TPM 限流。
5. **任务路由**。按任务选模型档位：大纲/命名/润色用廉价小模型，正文用旗舰，审查用推理模型；原则是"在质量底线内选最便宜"（Merge.dev 综述），并附加能力要求（如设定卡抽取必须 `structured_output`）。
6. **本地端点 = OpenAI 兼容端点**。Ollama（`http://localhost:11434/v1`）、llama.cpp（`llama-server`）、LM Studio（`:1234/v1`）、vLLM 均提供 OpenAI 兼容 HTTP 服务，天然落入同一抽象，是"零成本 / 离线 / 数据不出本机"的路径。
7. **密钥与配置主权**。多 Provider 配置只存 `key_ref` 引用而非明文；密钥本地加密存储、不上传（docs/01 §6），AI 调用默认关闭、逐项开启、输出可标识、使用可审计。

## 3. 可转化为产品规则的关键实践

1. Provider 描述文件（YAML）声明 protocol/base_url/auth/models/capabilities/limits → 设置面板按文件渲染，新增模型零改代码。
2. 能力矩阵驱动的"请求前校验" → 若任务要求 `structured_output` 而模型未声明，自动降级到"提示词约束 + JSON 后校验"路径并提示用户。
3. 任务路由表（outline/naming/polish/drafting/review → 档位） → 项目级可覆盖，默认"降价不掉质量"。
4. fallback 链 = 有序模型列表，支持跨 Provider 与本地兜底 → UI 可视化链路，节点显示健康度与冷却剩余。
5. 重试/冷却参数集中配置 → 失败自动退避、冷却期跳过该 Provider；UI 显示"openai 限流中，已切换"。
6. 并发/限流护栏 → 全局与每 Provider 并发上限、RPM/TPM 记账，超限排队而非硬失败（与 docs/01 §4.5 流式 AbortController 停止配合）。
7. 流式统一为 SSE 解析层 → 双端取消（用户停止 / 网络中断）不泄漏连接，`chunk` 缓冲交给前端 rAF 打字机。
8. API Key 只存 `key_ref` + OS 加密存储 → 导出项目/派系包自动剔除密钥；配置出现明文密钥即校验报错。

## 5. 对御书设计的启示

**数据结构建议：Provider 描述文件与能力矩阵**

```yaml
# providers/openai.yaml —— 单个 Provider 描述文件（项目级可覆盖）
id: openai
kind: cloud                      # cloud | local
protocol: openai_chat            # openai_chat | anthropic_messages | gemini_generate
base_url: https://api.openai.com/v1
auth: {type: bearer, key_ref: secret://openai/api_key}   # 仅存引用，不落明文
models:
  - name: gpt-5.6-luna
    tier: small                  # small | flagship | reasoning
    capabilities:                # 能力矩阵：驱动请求前校验与自动降级
      tools: true
      structured_output: true
      stream: true
      usage: true
      reasoning: false
      vision: true
      cache: {mode: explicit, min_tokens: 1024, read_mult: 0.1, write_mult: 1.25}
      batch: true
    limits: {context: 270000, max_output: 16384, rpm: 500, tpm: 900000}
```

**数据结构建议：任务路由与可靠性配置**

```yaml
# config/routing.yaml
routes:
  outline:  {prefer: [tier: small],    require: [structured_output]}
  naming:   {prefer: [tier: small]}
  polish:   {prefer: [tier: small]}
  drafting: {prefer: [tier: flagship], require: [stream]}
  review:   {prefer: [tier: reasoning]}
fallback:                                  # 主 → 备 → 本地兜底，顺序即优先级
  drafting: [gpt-5.6-luna, ollama/qwen3:14b]
reliability:
  num_retries: 3
  retry_policy: {RateLimitError: {max_retries: 5, backoff: exp}, InternalServerError: {max_retries: 3}}
  cooldown: {allowed_fails: 3, window_s: 60, cooldown_s: 30}
  concurrency: {global: 4, per_provider: {openai: 2, ollama: 1}}
```

**功能建议**
- Provider 管理器：文件驱动，支持连通性测试与"扫描本地端点可用模型"（Ollama/vLLM/LM Studio 自动发现）。
- 路由与 fallback 面板：可视化链路 + 每节点健康度/冷却倒计时 + 上次降级原因（如"openai 429 → 已切 luna"）。
- 上下文预览器联动（docs/01 §4.3）：显示实际发出的 provider/model/参数，便于排查"某模型不支持 tools"。

**校验规则建议**
- `provider-capability-mismatch`：任务 `require` 与模型 `capabilities` 不符且无可用降级 → error。
- `provider-key-plaintext`：配置文件出现明文 API Key（无 `key_ref`）→ error。
- `provider-fallback-cycle`：fallback 链存在环引用 → error。
- `provider-localhost-remote`：`kind: cloud` 的 base_url 指向 localhost/私网 → warn（数据主权提示，见 docs/01 §6）。
- `provider-concurrency-overflow`：`per_provider` 并发之和或单项 > `global` → warn。

**AI 提示词建议**
- 「模型能力问答」：输入某 OpenAI 兼容端点的 `/v1/models` 响应与报错文本，输出"该端点实际支持/不支持哪些字段"与降级建议。
- 「任务路由建议」：输入任务类型与质量要求，输出 `routes` 片段（含 require 能力与 fallback 链）。
- 「连通性诊断」：输入 curl 结果与错误码，输出是 base_url 拼接、鉴权还是协议差异问题。
