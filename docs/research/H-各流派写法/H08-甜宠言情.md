# H08-甜宠言情（总裁 / 豪门 / 婚恋）

> 类别：H-各流派写法 ｜ 世界构建金字塔层级：叙事层 · 流派写法
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究女频第一基调赛道"甜宠"在现言背景下的写法：以安全感与心动为核心情绪供给，低冲突、高糖密度、误会快速解开的类型。覆盖现代言情下的总裁文、豪门婚恋、契约婚姻/先婚后爱、破镜重圆、追妻火葬场等标签形态。边界：虐恋基调（刀糖交替）只作为黑时刻变体纳入；时代背景移到古代的言情归 H09；感情线形态（单 CP/多 CP/无 CP）按 docs/05 §1 是独立开关，不随本派系包强制。甜宠文的"糖"不是剧情稀薄，而是把冲突压缩进"关系内部"——误会、身份差、契约条款，这决定了它与世界维流派完全不同的节拍结构。

## 2. 核心知识框架

1. **言情节拍理论（西方 Romance Beat）**：Gwen Hayes《Romancing the Beat》四阶段（初遇坠入 → 关系深化 → black moment 决裂 → 复合收束）；Jami Gold 把言情弧线叠加在救猫咪式节拍表上形成独立的 Romance Planning Beat Sheet。主干 spine：Meet Cute → Stuck Together → Uh-Oh → Midpoint → Black/Dark Moment → Grand Gesture → HEA。言情文有三条并行弧线：外部情节弧、人物成长弧、关系弧，关系弧是主线。
2. **糖点机制**：甜宠的情绪供给=安全感+心动；糖点是"双向在意"的细节外化（护短、偏爱、吃醋、公开维护、日常照顾）。发糖需要节奏感——开源写作手册 webnovel-handbook 明确"发糖/幽默不能用段子挤占主线"，糖点必须挂在关系推进节点上而非随机撒。
3. **契约婚姻/先婚后爱弧线**：契约起点（利益交换/家族压力/闪婚，条款明确）→ 身份错位与防备猜忌 → 被迫共处中逐渐破防 → 双向奔赴反转；外部事件（女配作梗、商业阴谋、家庭危机）作为感情推进器。短剧改编验证了这条弧线的普适性。
4. **追妻火葬场变体**：爽感本质是"延迟兑现的情绪清算"——女主说"你不配"时，读者代入的不是被爱，而是"终于不必解释自己为何值得被善待"。开篇需交代契约底盘：婚姻年限、见面频率、当初的交易条件、婆媳关系。
5. **标签即类型承诺**：免费平台（番茄）以"甜宠/穿越/双洁"标签组织女频，豆瓣阅读以"破镜重圆/先婚后爱"等情感标签组织选题；平台标签体系与男频差异研究（中国作家网）表明男女频差异在叙事视角与爽点设计而非题材本身。

## 3. 可转化为产品规则的关键实践

**世界预设要点**
1. 甜宠世界=低威胁现实世界+权力场：豪门/总裁的金钱与地位差是糖点放大器 → 世界向导提供"豪门权力场"预设模板（家族企业/联姻格局/婚约关系网）。
2. 女主事业线必填：现代甜宠趋势是女主从被动承受转向独当一面 → 世界预设中女主职业与独立目标为必填字段。

**设定卡 schema 扩展（甜宠特有卡）**
3. CP 档案卡（双方人设、心动触发点、雷点、契约条款、关系阶段）→ 派系包 schema_extensions 的核心卡。
4. 糖点库卡（类型[护短/偏爱/吃醋/日常照顾/公开维护]/触发条件/强度/是否消耗误会预算）→ 发糖素材库。
5. 误会卡（起因/信息差来源/解开后影响/最长存续章数）→ 甜宠误会寿命天然短于虐恋。

**校验规则**
6. 误会寿命校验：单个误会跨度超过默认 8 章未解开 → warn"误会拖延，甜宠读者流失"。
7. 糖点间隔校验：连续 3 章无糖点且无外部冲突推进 → warn"糖点断供"。
8. 黑时刻配额：black moment 全书至多 1 次且篇幅受控 → 基调一致性 lint（甜宠≠虐恋）。

**写法指南与节拍**
9. 言情节拍表 YAML（meet_cute/stuck_together/midpoint/black_moment/grand_gesture/HEA）→ 节拍清单+进度打点+缺失提醒（联动 F 系节拍工程）。
10. 契约婚姻开篇模板：三章内交代契约条款+首次被迫共处+第一次破防 → 开篇设计模板库（联动 F11 黄金三章）。

**读者期待与雷点**
11. 期待=双向奔赴/偏爱细节/身份维护/确定 HEA；雷点=男主暧昧多人、误会拖沓、女主降智恋爱脑、强制情节、发糖靠旁白不靠细节 → taboos 清单与雷点 lint。

**AI 提示词倾向**
12. 糖点生成时注入"当前关系阶段+契约条款状态"结构化上下文，防止 AI 写出越阶段亲昵。
13. 发糖场景按"细节动作+心理独白+对话留白"三件套生成，禁令：不堆砌直白告白、不借旁白夸"他很宠她"。

## 5. 对御书设计的启示

**数据结构建议：甜宠派系包核心卡 schema**

```yaml
# schemas/CP档案卡.yaml —— 关系弧的结构化底座（甜宠特有）
extends: core/setting-card
fields:
  members: {type: array}            # 双方人物卡引用
  stage: {enum: [契约期, 破防期, 暧昧期, 确认期, 婚后]}   # 关系阶段（驱动校验与提示词）
  contract: {type: object}          # 契约条款：期限/条件/违约后果（契约婚变体）
  sugar_bank: {type: array}         # 已投放糖点（引用糖点库卡 ID）
  misunderstanding: {type: array}   # 活跃误会及其最长存续章数
```

**功能建议**
- 关系弧进度条：以言情节拍表为轨道，正文每章打点，black_moment 未到 Midpoint 就触发 → 顺序校验。
- 糖点库与"发糖按钮"：生成章节时按关系阶段推荐可用糖点类型，避免"契约期写婚后糖"。

**校验规则建议**
- `misunderstanding-expiry`：误会卡存续超期 → warn（甜宠默认 8 章，虐恋包可放宽）。
- `sugar-drought`：糖点断供检测（默认 3 章）。
- `tone-black-moment-quota`：黑时刻配额检查，甜宠包默认 1。

**AI 提示词建议**
- 续写模板注入状态块："关系阶段{stage}，活跃误会{mis}，本章情绪目标{发糖|铺垫|小波折}"。
- 发糖三件套模板强制细节动作先行，负面约束附读者原话级雷点（"别让男主舔屏式深情"）。
