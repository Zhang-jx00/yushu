# K09-全文检索与中文分词

> 类别：K-软件工程与产品 ｜ 世界构建金字塔层级：工程层 · 软件工程
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究本地优先写作工具里"在百万字全库中秒级定位一段文字"的全文检索工程，以及中文文本如何被切分成可索引的词元（token）。边界划分：J04 研究 RAG 混合检索（向量 + 关键词融合、切块、重排），本领域只负责其中的关键词一路——FTS5 索引、分词器、查询语法、索引增量更新与检索性能；K13 研究整体大文档性能预算，本领域聚焦检索侧；K02 管编辑器的命中高亮与跳转等交互侧。核心工程问题：SQLite FTS5 如何与"Markdown 真源 + 索引可重建"基线（docs/01 §6）对齐；中文没有空格，选单字、词还是 N-gram；分词精度如何影响召回；章节保存到索引可见的延迟如何定。

## 2. 核心知识框架

1. **FTS5 与 external content 表**。FTS5 是 SQLite 官方全文检索虚表：`CREATE VIRTUAL TABLE ... USING fts5(...)` 建表，`MATCH` 查询，`bm25()` 排序，`highlight()`/`snippet()` 高亮取上下文，并支持 `optimize`/`merge`/`rebuild`/`integrity-check` 等特殊命令。`external content` 表（`content='chunks', content_rowid='id'`）不重复存储正文，索引只是正文的派生物，`INSERT INTO fts(fts) VALUES('rebuild')` 可随时从真源全量重建——这正是 docs/01 §6"删除索引不丢任何数据"的官方级依据。
2. **tokenizer 的边界**。FTS5 内置 `unicode61`/`ascii`/`porter`/`trigram`。`unicode61` 按 Unicode 规则分词，对连续汉字会整段当作一个 token，"标题+内容"式查询基本失效；`trigram` 生成所有三字符子串，可支持 `LIKE '%子串%'` 式子串/模糊匹配，但索引膨胀且短词（<3 字）无法命中。两者都不懂中文词边界，故中文必须外挂分词器。
3. **中文分词三路线**。① 单字索引 + 查询改写：正文逐字索引，查询时把用户输入按词典切成词再拼成短语查询，`wangfenjin/simple` 即此路线（封装 cppjieba，提供 `simple_query()`/`jieba_query()` 自动组装 MATCH、`simple_highlight()` 连续高亮）；② 词索引：直接以 jieba 等分词器输出的词为 token，索引小但未登录词（角色名、自造功法名）易漏；③ N-gram（bigram/trigram）索引：不依赖词典、召回稳，代价是索引尺寸与短词噪声（`sqlite-cjk-fts` 即 CJK bigram 方案）。
4. **分词精度与召回**。召回漏失主要来自"查询切词 ≠ 索引切词"：用户搜"林渊"而索引把"林渊"切成"林/渊"，或搜"青莲剑诀"而词典未收该词。工程共识是索引侧尽量细（单字/双字）、查询侧尽量准（词典 + 同义词 + 短语约束），用查询改写抹平两侧粒度差；拼音/繁简/异体字是中文检索特有的召回补充（与 C09 命名体系、OpenCC 联动）。
5. **索引构建与增量更新**。索引既为派生物，更新分三档：章节保存即增量写（对应行 `INSERT`/`DELETE` 或触发器）、批量导入或换分词器时全量 `rebuild`、定期 `optimize` 合并段以控制查询退化。增量依据是 `mtime + hash` 组成的 `file_index`（与 J04 共用），重建须能后台执行并回报进度。
6. **查询语法与高级检索**。FTS5 支持短语（双引号）、前缀（`token*`）、NEAR、列过滤（`{col}:`）、布尔（AND/OR/NOT）与 `bm25` 加权排序；结果可经 `highlight()`/`snippet()` 带出上下文与命中位置，供 UI 高亮与跳回源章节。
7. **性能基准**。检索是本地交互功能，预算应内建：章节保存到可检索的延迟（百毫秒级）、单次查询 P95（几十毫秒级）、全量重建吞吐（按字数线性估计）。基准脚本以"百万字项目"为固定负载（与 K13 性能预算表共用同一份 fixture）。

## 3. 可转化为产品规则的关键实践

1. FTS5 用 external content 表建索引 → 建库脚本固定 `content=...` 与 `rebuild` 通道，索引可删可重建（对应 docs/01 §6）。
2. 中文 tokenizer 优先评估 `wangfenjin/simple`（全平台预编译、拼音可选）→ 作为默认 tokenizer；备选 CJK bigram 与 trigram，在项目配置中可切换（切换即触发全量重建）。
3. 索引侧细粒度 + 查询侧词典 → 打开 `simple_query`/`jieba_query` 自动组装 MATCH，不让用户手写 FTS5 语法。
4. 术语词典从设定库自动生成 → 角色名/地名/功法名/势力名作为自定义词条灌入分词器，与 C09、J05 共享术语表。
5. 章节保存即增量索引 → 编辑器 debounce 保存后写索引队列；异常/断电后补跑；`file_index` 记录 mtime+hash。
6. 批量重建带进度、后台执行 → 导入（I09）、换 tokenizer、索引损坏自愈三条路径共用同一重建向导。
7. 高级检索面板 → 短语/前缀/布尔/范围 + 卷/章节/实体过滤，查询语法对用户透明。
8. 结果高亮与跳转 → `highlight()`/`snippet()` 输出命中位置，点击跳回源章节并定位（与 J04 出处卡片同构，反幻觉用）。
9. 检索性能基准进 CI → 固定"百万字项目"负载跑查询延迟与重建吞吐，超预算即失败（与 K13 联动）。
10. 索引健康检查 → `integrity-check` + 源/索引 hash 对比，发现陈旧/损坏即提示一键重建。

## 5. 对御书设计的启示

**数据结构建议：FTS5 索引 schema 草案（`.yushu/index.sqlite`，索引可删可重建）**

```sql
-- 真源：Markdown + YAML frontmatter；索引仅为派生物（docs/01 §6）
CREATE TABLE chunks (
  id         TEXT PRIMARY KEY,     -- ch-012#scene-03
  chapter_id TEXT NOT NULL,
  volume     TEXT,
  kind       TEXT,                 -- chapter | scene | paragraph
  text       TEXT NOT NULL,
  char_start INTEGER, char_end INTEGER,
  text_hash  TEXT,                 -- sha256，增量依据
  entities   TEXT,                 -- JSON 数组，供实体过滤
  tokens     INTEGER
);
CREATE VIRTUAL TABLE chunks_fts USING fts5(
  text, entities UNINDEXED,
  content='chunks', content_rowid='id',
  tokenize='simple'                -- 中文+拼音；可切 trigram / cjk_bigram
);
CREATE TABLE file_index (path TEXT PRIMARY KEY, mtime TEXT, hash TEXT, indexed_at TEXT);
```

```yaml
# 项目配置 .yushu/config.yaml 的检索段
search:
  tokenizer: simple            # simple | trigram | cjk_bigram
  pinyin: false                # simple 的拼音开关
  query_fn: jieba_query        # simple_query | jieba_query | raw
  term_dict: .yushu/terms.txt  # 由设定库导出的自定义词条
  index_on_save: true
  rebuild: {background: true, batch: 500}
  budget: {query_p95_ms: 80, index_lag_ms: 500, rebuild_cpm: 20000}  # 字/分钟
```

**查询示例（检索管线只引用 J04，不在此重复）**
```sql
SELECT id, highlight(chunks_fts, 0, '<em>', '</em>') AS hl,
       snippet(chunks_fts, 0, '[', ']', '…', 12) AS snip, bm25(chunks_fts) AS score
FROM chunks_fts
WHERE chunks_fts MATCH jieba_query(?)          -- simple 扩展函数
  AND entities LIKE '%char-linyuan%'
ORDER BY score LIMIT 50;
```

**校验规则建议**
- `index-tokenizer-mismatch`：`config.search.tokenizer` 与实际建表 tokenize 不一致 → error，强制重建。
- `index-stale`：`file_index.hash` 与源文件 hash 不符 → warn，提示增量重建。
- `index-integrity-fail`：`INSERT INTO chunks_fts(chunks_fts) VALUES('integrity-check')` 报错 → error，走自愈重建。
- `term-dict-missing-word`：设定库实体名未出现在 `terms.txt` → info，提示补入以提高召回。
- `search-budget-exceeded`：基准脚本中 query P95 超预算 → error（CI 门槛，引用 K13）。

**功能建议**
- 全局搜索面板：短语/前缀/布尔/范围 + 卷/章节/实体过滤，语法对用户透明（由 `simple_query` 组装）。
- 术语词典自动同步：设定卡新增实体即刷新 `terms.txt`，并重建受影响分片。
- 索引重建向导：显示"将重算 N 文件 / 预计耗时 / 当前 tokenizer"，支持后台执行与进度。
- 搜索结果即出处：命中片段高亮 + 一键跳回源章节定位（与 J04 出处卡片同构）。

**AI 提示词建议**
- 「查询改写」：把自然语言检索意图改写成 3~5 条 FTS5 可执行查询（含专名、同义词、拼音），提升召回（与 J04 共用）。
- 「术语扩充」：从章节正文抽取疑似专名，输出候选词条写入 `terms.txt`。
