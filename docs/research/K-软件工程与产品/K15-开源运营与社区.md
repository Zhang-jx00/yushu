# K15-开源运营与社区

> 类别：K-软件工程与产品 ｜ 世界构建金字塔层级：工程层 · 软件工程
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究开源项目的「非代码基础设施」：许可证选型与贡献者授权、贡献指南与行为准则、版本发布与变更日志、issue/PR 流程、社区治理与决策记录、派系包与插件的社区分享规范、中文开源社区的特殊性，以及可持续性与商业化边界。边界：本领域只回答「社区与运营制度怎么定」，不回答「技术架构怎么选」（K12/K13）与「商业模式具体定价」；派系包的数据结构见 G06，插件扩展点见 docs/01 §4.10。核心工程问题：御书同时具备「桌面应用 + 插件系统 + 可分享派系包 + 可选云备份」四种形态，许可证需要在「保护核心开源」与「允许派系包/插件自由再用」之间取得兼容；同时社区治理必须轻到一个人也能维护、又足以支撑外部贡献者长期参与。直接对应 docs/01 §1（开源定位）与 §4.10（社区运营：贡献指南、Roadmap、行为准则、派系包分享规范）。

## 2. 核心知识框架

1. **许可证光谱与取舍**。choosealicense 按条件数量排序：AGPLv3（最强 copyleft，且「网络使用即分发」要求提供修改版完整源码）→ GPLv3（强 copyleft，同一许可、须公开源码）→ LGPLv3（库级弱 copyleft，通过接口使用可不同许可）→ MPL-2.0（文件级弱 copyleft）→ Apache-2.0（宽松 + 显式专利授权 + 州变更声明）→ MIT（最短宽松，仅保留版权与许可声明）。对御书的关键约束：若核心采用 GPL/AGPL，则派系包与插件的「衍生作品」判定会引发争议，可能吓退商业插件作者；若核心采用 MIT/Apache-2.0，则无力阻止闭源分叉。常见折中是「内核宽松（MIT/Apache-2.0）+ 品牌与官方分发受商标约束」，或「核心 GPL + 明确声明「派系包为数据、插件通过稳定 API 交互」，以降低衍生争议。
2. **贡献者授权：CLA vs DCO**。DCO（Developer Certificate of Origin 1.1）是一份单向声明而非合同、也不是许可证，贡献者在每次提交附 `Signed-off-by: 姓名 <邮箱>`（`git commit -s`）即表示满足 (a)(b)(c) 三种来源情形之一，并认可 (d) 贡献记录将永久公开留存；Linux Foundation 把它概括为「inbound == outbound」（项目从贡献者获得的授权范围 = 项目对外提供的授权范围）。CLA 则需单独签署授权协议（可能含版权转让或再许可权）。轻量项目优先 DCO + 自动 DCO 检查 Action；若未来需要「双许可/商业授权」再考虑 CLA。
3. **贡献指南与行为准则**。opensource.guide 的实践清单：先开 issue 再动手、PR 要引用 issue（`Closes #37`）、附前后截图、跑测试、主动请求反馈；并强调「非代码贡献（文档、翻译、设计、社区）同样关键」。Contributor Covenant 是全球采用最广的开源行为准则（v2.1 含承诺、准则、落实义务、适用范围、举报流程与四级处理阶梯——督促/警告/临时封禁/永久开除；v3.0 进一步明确「受珍视的行为」与「禁止的行为」二分），官方提供 40+ 语言译本与交互式定制器，中文版可直接采用。GitHub 侧把这些落成社区健康文件：`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SECURITY.md`、`ISSUE_TEMPLATE/*`、`PULL_REQUEST_TEMPLATE.md`，可放进 `.github` 仓库作为全组织默认。
4. **版本发布：SemVer + CHANGELOG**。SemVer 2.0.0（中文官方译本）规定 `X.Y.Z`：不兼容的公共 API 变更升主版本号、向下兼容的新增升次版本号、向下兼容的修复升修订号；`0.y.z` 为初始开发期，API 不应视为稳定；预发布标识（`-alpha.1`）与构建元数据（`+001`）为扩展。Keep a Changelog 规定 `CHANGELOG.md` 最新版本在前、日期用 ISO 8601、顶部保留 `Unreleased` 段、版本标题带 compare 链接、被撤回的版本标 `[YANKED]`，条目归入六类：Added / Changed / Deprecated / Removed / Fixed / Security（绝不新增第七类），并强调「变更日志是给人看的，不要直接 dump git log」「可以省掉功能公告，但绝不能省掉弃用、移除与破坏性变更」。Common Changelog 是更严格的子集，要求 `CHANGELOG.md` 文件名、每条变更可链接、并提出「先清理 git 历史再写日志」。
5. **issue/PR 流程与治理**。GitHub 的 issue 模板用 YAML 表单（`type: checkboxes` 等）强制填写复现步骤、环境、是否同意行为准则，并可用 `config.yml` 定制模板选择器；PR 模板要求关联 issue、说明动机与测试计划。治理上，Rust 的做法值得整体参照：**每一个重大决定都从一份 RFC 开始**，全员参与讨论权衡，进入「最终评论期（FCP）」后才采纳；同时设置 Leadership council（跨顶层团队代表）、各领域团队与**独立 moderation team**（负责执行行为准则与调解冲突）。
6. **决策记录（ADR）**。ADR 用一份短文档捕获单个架构决策及其理由与代价；MADR（Markdown ADR）是通行模板，包含上下文与问题、考虑过的方案及利弊、决定、后果、状态（Proposed/Accepted/Deprecated/Superseded）等字段；Nygard 原版为「标题/状态/背景/决定/后果」，Y-Statement 则是一句话式：「在 `<场景>` 下，面对 `<问题>`，我们选择 `<方案>` 以达到 `<目标>`，接受 `<代价>`」。adr.github.io 建议把一整套 ADR 作为项目的 `decision log`。
7. **派系包与插件的社区分享规范**。参照既有生态：Minecraft 数据包 / Stardew Content Patcher 证明「命名空间隔离 + 稳定 ID + 覆写/补丁分层」是可分享内容的通用骨架（见 G06）；Obsidian / SillyTavern 的插件生态表明社区目录需要「命名空间 + 版本兼容区间 + 安全声明（是否联网、是否执行外部代码）+ 审核状态」。御书需在此之上增加创作领域特有的「内容分级」与「安全审核」：派系包可能携带 AI 提示词模板与规则 DSL，插件可能申请「AI 任务」与「文件系统」权限。
8. **中文开源社区的特殊性**。Gitee《开源指北》的贡献流程以「Fork + PR」或「轻量级 PR」为主，辅以 issue 认领（评论「姓名 + 预计完成时间 + 备注」），并对文章格式（Markdown）与编写规范单独成文；开源社以「贡献 / 共识 / 共治」三原则运营，定位「厂商中立、公益、非营利」，并把「国际桥梁」与「社区发展」并列为使命。实践含义：① 沟通渠道需同时覆盖 GitHub（issue/PR）与国内即时通讯（微信/QQ 群、Gitee 镜像）；② 文档应中英双语，中文为一等公民；③ 贡献门槛要低（允许轻量级 PR 与文档/翻译贡献）。
9. **可持续性与商业化边界**。开源不等于无成本：CI、代码签名、文档站、模型 API 额度都是持续支出。可持续路径包括捐赠/赞助、付费托管与云备份、企业支持、周边与培训、品牌授权；底线是不牺牲数据主权与核心可用性——docs/01 §5 已明确「不做云端账号强制体系」「不替代平台发布流程」「AI 默认关闭」，故商业化只能落在「可选服务」而非「核心功能上锁」。

## 3. 可转化为产品规则的关键实践

1. 许可证决策表（内核 + 数据 + 生态）→ LICENSE 与 NOTICE 三份文件分离：内核许可证、派系包内容许可证（建议 CC-BY-SA 类）、示例素材许可证。
2. 采用 DCO 而非 CLA（轻量项目最优解）→ 启用 `Signed-off-by` 检查 Action，`CONTRIBUTING.md` 写明 `git commit -s`；未来若需双许可再叠加 CLA。
3. 四份社区健康文件齐备（GitHub 社区档案）→ `CONTRIBUTING.md` / `CODE_OF_CONDUCT.md`（Contributor Covenant 2.1 中文版）/ `SECURITY.md` / `GOVERNANCE.md`，放入 `.github` 仓库统一维护。
4. Contributor Covenant 四级处理阶梯 → 社区管理流程写明「督促→警告→临时封禁→永久开除」与举报邮箱、保密义务。
5. SemVer + 引擎兼容区间（G06 的 `requires.yushu`）→ 引擎与派系包/插件各自独立 SemVer，包声明可运行区间，破坏性变更必须升主版本并附迁移脚本。
6. Keep a Changelog 六类 + Unreleased 段 → 仓库维护 `CHANGELOG.md`，发布流程要求「先写 Unreleased，再冻结为版本段」，禁止 dump commit log。
7. issue/PR 模板 + 标签体系 → 使用 YAML 表单模板，标签含 `good first issue`、`help wanted`、`type/*`、`area/*`、`status/*`；PR 模板强制「关联 issue + 测试/验证说明」。
8. RFC 流程（Rust 参照）→ 重大设计（如存储格式、扩展点、规则 DSL）先提 RFC，讨论后进入「最终评论期」，再落 ADR 归档结论。
9. ADR 决策日志（MADR/Y-Statement）→ `docs/adr/NNNN-*.md` 记录「背景/方案对比/决定/后果/状态」，新决定取代旧决定时更新 `Superseded by`。
10. 维护者梯队与模块 owner → `GOVERNANCE.md` 定义「贡献者 → 复审者 → 维护者 → 核心团队」路径与各领域 owner（编辑器/世界引擎/记忆系统/派系包工具链）。
11. 派系包分享规范（安全审核 + 命名空间 + 评分）→ 派系包 manifest 强制 `metadata.id` 作命名空间前缀（G06），提交工坊前跑 lint（schema/ID 唯一/11 件套齐全/映射覆盖）+ 权限声明 + 人工/自动审核。
12. 插件权限模型 → 插件 manifest 声明权限（filesystem / network / ai_task / editor_write），安装时显式告知，未声明即拒绝调用。
13. 中文一等公民 → 文档双语（中文为主 + 英文镜像）、GitHub + Gitee 双镜像、微信群/QQ 群 + Discussions 并行，贡献指南给出「轻量级 PR」与 issue 认领流程。
14. 可持续性边界 → 商业化只做「可选服务」（云备份、托管派系包市场、企业支持），核心离线能力永久免费，写入 `GOVERNANCE.md` 与 README 的承诺。

**校验规则建议（规则 id）**

- `oss-license-presence`：仓库根目录缺 `LICENSE` 或缺 SPDX 标识 → error。
- `oss-dco-signoff`：提交信息缺少 `Signed-off-by` → error（CI 拦截）。
- `oss-changelog-format`：`CHANGELOG.md` 缺少 `Unreleased` 段、版本标题缺 ISO 8601 日期，或出现六类之外的条目标题 → error。
- `oss-semver-bump`：公共 API（引擎接口/扩展点/包格式）发生不兼容变更但主版本未升 → error（对照 ADR 判定）。
- `oss-breaking-undocumented`：CHANGELOG 未记录弃用/移除/破坏性变更 → error（Keep a Changelog 底线）。
- `oss-code-of-conduct`：缺 `CODE_OF_CONDUCT.md` 或未填举报联系方式 → error；四份健康文件（CONTRIBUTING / CODE_OF_CONDUCT / SECURITY / GOVERNANCE）任一缺失 → warn。
- `oss-issue-template`：`ISSUE_TEMPLATE/` 无 `config.yml` 或表单未含行为准则勾选项 → warn。
- `pack-id-namespace`：派系包/插件 `id` 与既有包冲突或非法字符 → error（命名空间隔离）。
- `pack-permissions-declared`：插件使用了未声明的权限能力（如未声明 `network` 却发起请求）→ error。
- `pack-license-missing`：派系包 `license` 为空或为衍生不兼容许可 → warn。
- `pack-eleven-piece`：派系包 11 件套存在缺项 → warn（对齐 docs/01 §3.2）。
- `oss-governance-stale`：`GOVERNANCE.md` 中维护者名单与实际 CODEOWNERS 不一致 → info。

**功能建议**
