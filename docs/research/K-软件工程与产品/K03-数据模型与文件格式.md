# K03-数据模型与文件格式

> 类别：K-软件工程与产品 ｜ 世界构建金字塔层级：工程层 · 软件工程
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究「用户数据在磁盘上长什么样」：正文与元数据的格式规范、项目目录布局、设定卡的结构校验、项目配置格式、索引与缓存数据库的边界、格式版本与迁移、以及对 Git 的友好性。边界划分：K02 管「内存文档模型」，本领域管「磁盘持久化结构与互操作性」；后者是数据主权承诺（docs/01 §6）的直接承载体——文件必须可读、可版本化、可迁移。与 J03（记忆系统分层）、J04（RAG）相邻：本领域只定义存储格式与校验，不定义检索算法。核心工程问题：如何让「一部小说 = 一个可被任何工具打开的文件树」，同时保留结构化能力（设定卡可校验、索引可重建、设定可被一致性引擎遍历）。

## 2. 核心知识框架

1. **Markdown + YAML frontmatter 作为真源**。Jekyll 的 frontmatter 是这一约定的事实起点：文件顶部由 `---` 包裹的 YAML 元数据块承载结构化字段，正文承载内容。它让「正文可读」与「元数据可编程」分离：人读正文、机器读 frontmatter。YAML 1.2.2 是现行规范（人类友好、跨语言、Unicode 数据序列化语言），但要注意其隐式类型与歧义风险（如 `yes/no`、日期解析），因此关键字段应显式加引号或限定类型。
2. **frontmatter 字段约定**。约定优于配置：`id`（稳定标识，跨文件引用锚点）、`type`（实体类型，决定用哪份 schema 校验）、`format_version`（格式版本，驱动迁移）、`aliases`（别名，供检索与提及匹配）、`links`（出链，供关系图谱构建）。字段名与 Obsidian Properties 保持兼容，可被 Obsidian/Logseq 直接打开。
3. **项目目录布局（开放格式实践）**。Obsidian 的 vault「就是一个文件夹」，「file over app」主张文件优先于应用、避免深目录、避免非标准 Markdown；Logseq 的 graph 收敛出 `pages/`（内容）、`journals/`（日记）、`assets/`（媒体）、`logseq/`（配置）四段式。二者共同经验：**内容用扁平或浅层目录 + 属性/链接组织，元数据与内容同文件共存**。御书的差异是「世界分层」，因此采用「分层目录（世界观各层）+ 章节扁平序号」的混合布局。
4. **JSON Schema 校验设定卡**。JSON Schema 2020-12 用 `$schema/$id/type/properties/required` 描述与校验 JSON 文档，JSON Schema 文档由 URI 标识、可 `$ref` 组合复用。设定卡在内存中是 JSON 对象，落盘为 YAML frontmatter，二者结构同构：YAML 解析后即交给 JSON Schema 校验，校验器返回布尔结果与错误路径。派系包（G06）通过扩展 schema 注入流派专属字段（境界体系、诡异档案、公司商业卡），需支持 `allOf` 合并与字段冲突检测。
5. **TOML 项目配置**。TOML v1.0.0 语义明显、无歧义地映射到哈希表、大小写敏感、必须 UTF-8，适合放「项目级开关」而非内容：派系包清单、AI 提供方与模型、导出目标、代码风格。内容（会频繁 diff、会被 AI 读写）用 Markdown+YAML，配置（改得少、机器读为主）用 TOML，这是 S8 的关键结论。
6. **SQLite 只做索引与缓存**。SQLite 官方论文《As An Application File Format》说明单文件库可作为应用格式，但御书只需它的索引能力：FTS5 的 external content 表可随时 `rebuild`，因此正文/设定卡改动后索引可整体重建；这直接兑现 docs/01 §6「删除索引不丢失任何数据」。WAL 模式提供读写并发（详见 K04），但索引库不得放在网盘同步目录。
7. **格式版本与迁移**。任何持久格式都会演化，必须自带版本号与迁移路径：每个文件 frontmatter 写 `format_version`，项目根写全局 `schema_version`；启动时扫描版本、对低版本文件执行幂等迁移脚本、迁移前自动备份。迁移必须可回滚、可中断续跑、幂等——与 I09（存量稿件迁移）共用同一套迁移框架。
8. **Git 友好性**。纯文本 + 小文件 + 稳定换行 + 每行语义单一（避免超长单行）才能产生有意义的 diff。要避免的：二进制（图片用 `assets/` 并配 LFS 说明）、把大对象塞进 frontmatter、随机排序导致的无意义 diff（字段顺序固定、列表排序稳定）、在内容文件里放时间戳（每次保存都变更，可选放在单独文件）。

## 3. 可转化为产品规则的关键实践

1. 正文与设定卡均为 Markdown + YAML frontmatter → 落盘格式统一，人可读、Git 可 diff、任何编辑器可打开（docs/01 §6）。
2. frontmatter 固定字段集与顺序 → 序列化时按固定键序输出，减少无意义 diff；`id/type/format_version` 为必备字段。
3. 项目目录分层布局 → 世界观各层一目录、章节按卷分目录 + 连续序号文件，媒体进 `assets/`（见 §5 目录树）。
4. 设定卡用 JSON Schema 校验 → 内存为 JSON、落盘为 YAML，用同一份 schema 校验；派系包以 `allOf` 扩展（G06 联动）。
5. 项目配置用 TOML → 派系包清单、AI 提供方、导出目标集中在一个 `.toml`，与内容解耦。
6. SQLite 仅作索引/缓存 → 表结构由文件推导，提供「重建索引」命令；索引库路径排除于同步目录。
7. 格式版本与迁移 → 每文件 `format_version`、项目 `schema_version`，迁移脚本幂等 + 自动备份 + 可回滚。
8. Git 友好序列化 → 固定字段序、稳定列表排序、LF 换行、UTF-8 无 BOM、正文不写时间戳。
9. 跨工具互操作 → 保持 Obsidian/Logseq 兼容的 frontmatter 与链接语法，用户可随时用第三方工具接管。
10. 二进制素材外置 → 图片/音频放 `assets/` 并在项目中声明 Git LFS 建议，正文只存相对路径引用。

## 5. 对御书设计的启示

**数据结构建议：项目目录树（草案）**

```text
my-novel/                        # 项目根 = 一个世界（docs/01 §2）
├── project.toml                 # 项目配置（派系包/AI/导出，见下）
├── world/                       # 世界观分层（对应 A/B/C/D/E 类）
│   ├── genesis.md                      # 起源与法则（A）
│   ├── geography/continent-east.md     # 地理生态（B）
│   ├── history/era-01-founding.md      # 历史纪元（C）
│   ├── power/realm-levels.md           # 力量与文明（D，派系包扩展）
│   └── entities/char-linyuan.md        # 记忆系统实体（E，设定卡）
├── outline/master.md  vol1.md  ch-012.md   # 三级大纲（I02）
├── chapters/vol1/ch-012.md      # 正文（I01：连续序号、卷目录）
├── assets/                      # 图片/音频（Git LFS 建议）
├── packs/xuanhuan-system/       # 派系包（G06）
├── schemas/                     # JSON Schema（设定卡/章节/派系包）
└── .yushu/                      # 应用内部（索引缓存，不进 Git、不同步）
    ├── index.db  index.db-wal  index.db-shm
    └── backups/
```

**设定卡 schema 草案（YAML frontmatter + JSON Schema 校验）**

```yaml
# world/entities/char-linyuan.md
---
id: char-linyuan
type: character                # 决定用哪份 JSON Schema 校验
format_version: 1
title: 林渊
aliases: [林师弟, 渊哥]         # 供提及匹配与检索（J03/J04）
tags: [characters, protagonist]
traits: { realm: 筑基期, age: 19 }
links:
  faction: faction-qingyun     # 出链 → 关系图谱（E03）
  location: loc-cangjingge
narrative_visibility: hidden   # 冰山原则：已写未揭示（docs/01 §4.2）
source_chapters: [ch-012]
---
（正文：人物档案自由文本）
```

对应的 JSON Schema（`schemas/character.schema.json`，节选）：`{"$schema":"https://json-schema.org/draft/2020-12/schema","type":"object","required":["id","type","format_version"],"properties":{"id":{"type":"string","pattern":"^char-[a-z0-9-]+$"},"type":{"const":"character"},"aliases":{"type":"array","items":{"type":"string"}}}}`。派系包通过 `allOf` 追加流派字段（玄幻追加 `cultivation_realm`，恐怖追加 `threat_level`）。

**project.toml 草案**

```toml
schema_version = 1                 # 项目级格式版本，驱动迁移
title = "青云志"
[genre]
packs = ["xuanhuan", "system-flow"]   # 派系包清单（G06）
[ai]
provider = "openai-compatible"
model_body = "gpt-flagship"
model_outline = "gpt-mini"          # 任务路由（J01）
[export]
formats = ["txt", "epub3", "docx"]
[editor]
autosave_ms = 800                   # 自动保存防抖（K04）
```

**迁移策略**：读取文件 → 比较 `format_version` 与引擎支持版本：相等直接加载；更低则备份到 `.yushu/backups/` → 执行幂等迁移脚本 → 回写新版本；更高则拒绝加载并提示升级应用（避免降级损坏）。

**校验规则建议**

- `format-version-missing`：文件缺 `format_version` → error（无法迁移判定）。
- `format-version-ahead`：`format_version` 高于引擎支持 → error，阻止写入以防降级损坏。
- `card-schema-invalid`：设定卡不通过对应 JSON Schema（缺 `id`/`type` 不合法/`id` 命名不符）→ error，列出 JSON Pointer 路径。
- `card-id-duplicate`：项目内 `id` 重复 → error（跨文件引用会指向错误对象）。
- `card-link-dangling`：`links.*` 指向的 `id` 不存在 → error（E03 关系图谱联动）。
- `path-convention-violation`：章节文件不在 `chapters/{volume}/` 或序号不连续 → warn（I01 联动）。
- `frontmatter-order-unstable`：序列化后字段顺序与规范不一致 → info（影响 Git diff 质量）。
- `git-binary-in-content`：正文目录出现二进制文件 → warn，提示移入 `assets/`。
- `index-not-rebuildable`：索引库存在但无法由文件完整重建 → error（违反 docs/01 §6 数据主权）。

**功能建议**

- 「重建索引」命令：随时从文件全量重建 `.yushu/index.db`，并给出「删除索引零数据丢失」的可验证提示。
- 格式迁移器：升级应用时批量迁移并生成迁移报告；迁移失败的单个文件隔离列出，不阻塞其余文件（与 I09 存量导入共用框架）。
- Schema 编辑器：派系包作者可视化扩展设定卡 schema（G06 派系包工坊），保存时检测与已有字段冲突。
- 互操作导出：一键把项目目录导出为「Obsidian 可直接打开」的兼容结构（保持 frontmatter 字段名）。
- 配置文件不写内容：任何「项目事实」必须落在 Markdown/设定卡，TOML 只留开关与清单。

**AI 提示词建议**

- 「设定卡抽取」：从正文段落抽取实体，输出符合 card schema 的 frontmatter 草案（结构化输出，J06），字段名与类型严格对齐 schema。
- 「frontmatter 规范化」：把自由格式的元数据改写为规范字段序与类型（引号化歧义标量）。

## 6. 领域内子主题备忘（可选）

- JSON Canvas（`.canvas`）作为空间卡片/看板的开放互操作格式（可视化与大纲联动）。
- YAML 多行字符串、锚点/别名在 frontmatter 中的可用性与编辑器兼容风险。
- 项目内二进制素材的 Git LFS 策略与云备份（WebDAV/S3）配合。
- `js-yaml`/`gray-matter` 等解析库在解析失败时的容错与提示体验。
- 多项目（多本书）之间的设定复用：共享库 vs 独立副本的取舍。
- 跨端预留：文件名大小写敏感、路径长度、非法字符在各系统的差异。
