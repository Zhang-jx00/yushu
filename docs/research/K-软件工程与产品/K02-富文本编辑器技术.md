# K02-富文本编辑器技术

> 类别：K-软件工程与产品 ｜ 世界构建金字塔层级：工程层 · 软件工程
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究「正文写作界面」的底层技术：结构化文档模型（schema + 节点树 + 事务）、富文本视图与源码视图的双形态同步、结构化文档与 Markdown 的序列化往返、大文档渲染性能，以及为远期协作预留的数据结构。边界划分：K03 管「文件格式与磁盘结构」，本领域只管「内存中的文档模型与编辑交互」，两者的契约是「结构化文档为唯一真源、Markdown 为序列化产物」（docs/01 §4.7）。与 I02（大纲编辑）、J08（流式写作 UX）相邻但不同：大纲卡片与 AI 流式插入都复用本文档模型，但交互范式各自研究。核心工程问题：如何用严格 schema 保证一致性引擎可遍历，如何在不丢信息的前提下输出人类可读的 Markdown，如何让同一文档在富文本与源码两种视图间同步而不产生格式漂移。

## 2. 核心知识框架

1. **ProseMirror 四大模块与单向数据流**。`prosemirror-model` 定义文档模型（schema 描述允许的节点与 mark），`prosemirror-state` 持有 `EditorState`（doc + selection + storedMarks + plugins），`prosemirror-transform` 提供可记录、可重放的修改（step），`prosemirror-view` 渲染并处理输入。所有更新经由唯一入口「事务（Transaction）」：`oldState + tr → newState`，状态不可变、渲染层订阅式同步，可类比 Redux 的 store/dispatch，但绝大多数事务由编辑器自身根据用户输入构造。
2. **严格 schema 是「结构化真源」的技术前提**。Tiptap 基于 ProseMirror schema，用内容表达式声明可嵌套关系（`block+` / `inline*` / `(paragraph|list?)+`），用 `group` 与 `marks` 约束。schema 极严格：未在 schema 中定义的元素在粘贴/解析时被直接丢弃（可监听 `contentError`）。这既是约束也是能力——数据库里永远只有你允许存在的节点，一致性引擎可安全遍历。
3. **扩展体系（Node / Mark / Extension 三层）**。Node 是块级或内联内容类型，Mark 作用于节点局部（加粗、链接），Extension 注册命令、快捷键、插件与视图。内联节点用 `inline: true` 渲染成「有节点能力、类 mark 外观」的元素（如 @提及），这是实体内联标记的官方推荐路径。
4. **装饰器（Decoration）：视图层的一切，不动文档**。三类：`Decoration.inline`（给文本段加 class/style）、`Decoration.widget`（在某个位置插入 DOM）、`Decoration.node`（给块节点加属性）。Decoration 是「临时的」，仅存在于视图层，通过 `DecorationSet.map()` 随事务映射，适合实时高亮、校对标错、实体悬停下划线等——不污染文档、不参与序列化。
5. **Markdown 序列化与保真度陷阱**。ProseMirror 官方作者 Marijn 明确说明：Markdown 往返转换是**有损**的（缩进、换行、列表符号、空行等），无法在 Markdown 编辑器与 ProseMirror 实例之间不经归一化地实时双向同步。因此业界收敛到「单一真源 + 单向序列化 + 归一化」，而非「两套格式互转」。表格、脚注、自定义节点若 Markdown 无原生语法，必须用扩展语法或降级策略显式定义。
6. **CodeMirror 6 的架构**。同样是不可变状态 + 事务（`EditorState` + `StateEffect/Annotation` + `StateField`），但模型是**纯文本 buffer**：`@lezer/markdown` 增量解析出语法树，插件（ViewPlugin）遍历该树生成 Decoration，隐藏/替换语法 token 即得「实时预览」。facet 是「可组合的扩展点」（如主题、只读、行高），Compartment 允许运行时只重配某一组扩展而不重建编辑器（保住撤销栈与光标）。
7. **双形态同步的两种路线**。①**同模型双视图**：结构化文档是真源，富文本视图直接渲染它，源码视图渲染其 Markdown 序列化结果，两者靠「文档 → Markdown」与「Markdown → 文档」的往返 + 归一化对齐（有损风险区在此）；②**单 buffer 装饰**：如 CM6/Milkdown 路线，磁盘 Markdown 即真源，富文本只是装饰层。御书选 ①（docs/01 §4.7），必须为往返建立可检测的保真损失边界。
8. **大文档性能的现实约束**。ProseMirror **不做视口虚拟化**，整篇文档进 DOM；社区实测 7 万 mark 的初始渲染约 700ms（无 mark 约 70ms），大量同时渲染的 decoration 会明显卡顿，官方建议由插件侧控制渲染范围（如先高亮选区附近、空闲再补全），而非期待库层做异步魔法。CodeMirror 6 则原生只渲染视口、增量解析，长文档更稳。官方核心原则：**渲染出的表示必须能被回解析还原文档**，因此不能用「不渲染某些 mark」的方式偷性能。
9. **协作的远期预留**。v1 不做多人协作（docs/01 §5），但文档模型若不堵死即可在后期接 Yjs：Yjs 以 CRDT 提供 `Y.XmlFragment/Y.Text` 等共享类型，已有 ProseMirror/TipTap 绑定，且天然支持离线合并。低成本预留 = 保持「文档为可序列化纯数据 + 所有修改走事务 + 节点带稳定 id」。

## 3. 可转化为产品规则的关键实践

1. 结构化文档为唯一真源、Markdown 为序列化产物 → 内存模型用 Tiptap/ProseMirror 节点树，磁盘只存序列化后的 `.md`（对应 docs/01 §4.7 与 K03 格式规范）。
2. 自定义 schema 只为「世界一致性引擎需要遍历的节点」开洞 → 设定卡引用、伏笔标记、大纲锚点必须有独立节点类型（带稳定 id），不可退化为纯文本标记。
3. 实体内联标记用内联节点 + 装饰器实现 → `@角色/地点` 为 `inline+atom` 节点，悬停/点击由插件处理；搜索高亮、校对标错一律走 Decoration，不写回文档。
4. Markdown 往返建立保真清单 → 明确哪些节点可无损往返、哪些需扩展语法、哪些不允许出现在正文（如复杂表格），序列化后做结构比对。
5. 双形态切换保持同一 doc → 富文本视图与源码视图共享同一 `EditorState`；切换时源码视图渲染序列化 Markdown，回切时解析并做差异最小化，避免整篇重排丢光标。
6. CodeMirror 6 作源码模式内核 → 主题/只读/行高用 facet，模式切换用 Compartment 重配而非重建，保留撤销栈与滚动位置。
7. 大文档按章节分文件 + 单章加载 → 编辑器只挂载当前章，跨章引用由大纲/记忆系统索引，避免「整本书 300 万字进 DOM」。
8. Decoration 渲染做范围收敛 → 全文搜索/一致性标注先只渲染选区可见区，空闲后再补全；设置渲染上限阈值并降级为「仅列表提示」。
9. 协作接口预留 → 节点模型序列化为纯 JSON、所有变更走事务、关键节点带 id 与相对位置，未来可整体接入 Yjs 而不改格式。

## 5. 对御书设计的启示

**数据结构建议：编辑器文档节点 → Markdown 映射表（草案）**

```yaml
# 源：docs/01 §4.7「结构化文档为唯一真源、Markdown 为序列化产物」
format_version: 1
node_map:
  doc:            { md: "整篇文档", block: true }
  paragraph:      { md: "段落（空行分隔）" }
  heading:        { md: "#{level} 标题" }
  bulletList:     { md: "- 列表项" }
  blockquote:     { md: "> 引用" }
  horizontalRule: { md: "---" }
  entityMention:  # 实体内联标记（@角色/地点），inline 原子节点
    md: "@[显示名](entity:type-id)"
    inline: true
    atom: true
    attrs: [entity_type, entity_id, display]   # entity_id 指向设定卡（E02/G06）
  foreshadowTag:  # 伏笔埋设/回收锚点（F08 联动）
    md: "[[fs:id]]"
    inline: true
    attrs: [foreshadow_id, role]               # role: plant | payoff
  footnoteRef:    { md: "[^n]", lossy: true }  # Markdown 无原生脚注，需扩展语法
  table:          { md: "GFM 表格", lossy: true }  # 复杂合并单元格不支持，正文内建议禁用
# 保真度分级：safe（无损）/ extended（御书扩展语法）/ lossy（禁止或降级）
```

**双形态同步约定**

```text
富文本视图 ──(同一 EditorState 的 doc)── 源码视图
    ▲                                        │
    │  doc → serialize() → Markdown           │ 用户编辑
    │  parse(Markdown) → doc（差异最小化）     ▼
    └────────────── 结构比对 / 保真校验 ───────┘
```

**功能建议**

- 编辑器内核统一用 Tiptap/ProseMirror，源码模式用 CodeMirror 6；两种模式共享同一份 `doc`，模式切换用 Compartment/重配而非重建，保住撤销栈与光标。
- 实体内联标记：输入 `@` 唤起设定卡（角色/地点/势力/物品）选择器，插入 `entityMention` 内联节点；悬停显示设定卡摘要，点击跳转记忆系统（E02/I02）。
- 一致性标注、敏感词高亮、错别字标红一律走 Decoration，绝不写回文档（J14 校对、I07 敏感词联动）。
- 大文档策略：正文按章节分文件、编辑器单章挂载；跨章检索由 K03 的 SQLite 索引承担。
- 「保真度体检」面板：导出/切源码模式前跑一次往返校验，列出 lossy 节点并给替代写法。
- 协作预留开关（v1 关闭）：保留「文档 → 纯 JSON」「事务化修改」「节点稳定 id」三条不变量，v1 不引入 Yjs 依赖（docs/01 §5）。

**校验规则建议**

- `format-roundtrip-loss`：`doc → Markdown → doc` 结构比对不一致（出现 safe 节点丢失/mark 漂移）→ error，定位到段落。
- `editor-lossy-node-in-article`：正文（`chapters/**`）出现 `lossy: true` 节点（如复杂表格、脚注）→ warn，提示改写为扩展语法或纯文本。
- `editor-entity-ref-missing`：`entityMention.entity_id` 在设定卡库中不存在 → error（与 G06/记忆系统联动）。
- `editor-foreshadow-ref-missing`：`foreshadowTag.foreshadow_id` 不在 F08 台账 → error。
- `editor-doc-single-huge-file`：单章序列化后字符数超过阈值（如 5 万）→ info，提示拆分或启用分片加载。
- `editor-decoration-overflow`：单次事务渲染 decoration 数超过阈值 → info，提示收敛渲染范围。

**AI 提示词建议**

- 「内联标记补全」：对选中段落识别可能应标记为 `entityMention` 的专名，输出候选（实体类型 + id + 依据），由用户确认后插入节点。
- 「保真改写」：把含 lossy 结构的段落改写为可无损往返的 Markdown 等价写法。
