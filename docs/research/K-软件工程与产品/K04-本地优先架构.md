# K04-本地优先架构

> 类别：K-软件工程与产品 ｜ 世界构建金字塔层级：工程层 · 软件工程
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究「数据主权如何落到系统架构上」：local-first 软件原则、Electron 进程边界与 IPC 契约、SQLite 的并发与持久化位置、文件系统监听与外部修改冲突、自动保存与崩溃恢复、离线能力边界。边界划分：K03 定义磁盘格式，本领域定义「谁在何时以何种权限读写这些文件」；K05（桌面应用工程）关注打包分发与更新，本领域关注运行时数据通路。核心工程问题：在「渲染层不直连文件系统」的安全前提下，如何让离线编辑体验无损、让崩溃几乎不丢稿、让外部工具（Git、Obsidian、编辑器）改动项目时系统不崩坏。

## 2. 核心知识框架

1. **local-first 七理想（Ink & Switch 2019）**。Kleppmann 等提出：①无转圈（本地即时应答）②数据不困于单一设备③网络可选（离线是正常状态）④无缝协作（未来）⑤长寿（数据比应用活得久）⑥默认安全与隐私⑦用户拥有最终控制权。论文的核心主张是「数据所有权与实时协作并不互斥」，并以 CRDT 作为落地技术。七理想可直接作为御书数据层的验收清单；御书 v1 取 ①②③⑤⑥⑦，把 ④ 列为远期（docs/01 §5）。
2. **文件优先（file over app）是 local-first 的格式侧印证**。Obsidian 的「vault 就是一个文件夹」、Logseq 的「graph 是目录 + 文件」都把应用降格为「数据的镜头」而非「数据的牢笼」。这为 docs/01 §6 的「Markdown 开放格式 + 可随时迁移」提供了同源实践。
3. **Electron 多进程模型**。Electron 继承 Chromium 的多进程架构：单一 **main 进程**（Node 环境，创建并管理 `BrowserWindow`、控制应用生命周期、调用原生 API）+ 每个窗口一个 **renderer 进程**（按 Web 标准跑 UI）。渲染进程崩溃不必然拖垮主进程，是「崩溃恢复」的进程级基础。
4. **context isolation 与 preload 安全边界**。自 Electron 12 起 `contextIsolation` 默认开启：preload 脚本运行在「隔离世界」，与页面主世界共享的 `window` 是不同的对象；跨边界只能通过 `contextBridge.exposeInMainWorld` 暴露 API，且传入值被**复制并冻结**、函数被代理。官方明确的反模式：直接暴露 `ipcRenderer.send`（允许任意网站发任意 IPC），正确做法是「一个 IPC 消息一个方法」（如 `loadPreferences: () => ipcRenderer.invoke('load-prefs')`）。由此确立御书铁律：**渲染层不直连文件系统，一切文件读写经主进程**。
5. **SQLite WAL 与并发**。WAL 模式下「读不阻塞写、写不阻塞读」，磁盘 I/O 更顺序、fsync 更少；但代价是：所有进程必须同机（**WAL 不能用于网络文件系统**，因为需要共享内存索 `-shm`）、附加 `-wal`/`-shm` 两个文件、需要 checkpoint、不适合超大事务（>100MB 反而更慢）。SQLite 的隔离模型是「串行化写」：同一时刻只有一个写者，多连接自动排队加锁。工程含义：**主进程独占写、渲染层只读查询**，索引库不放同步目录。
6. **文件系统监听与外部修改**。项目文件可能被 Git、Obsidian、任意编辑器改动。chokidar 抹平了 `fs.watch/fs.watchFile` 的平台差异：macOS 有 FSEvents、Linux 有 inotify、其他用轮询；它把事件规范为 `add/change/unlink`，并提供 `atomic`（识别「临时文件 + rename」的原子写，100ms 内重建判为 change 而非 unlink+add）与 `awaitWriteFinish`（等分块写完再发一次事件）。外部修改必须与内存状态做三方合并，冲突时不可静默覆盖。
7. **自动保存与崩溃恢复**。单靠「定时写文件」不足以防丢稿：写文件本身可能被中断。可靠做法是「dirty flag + debounce 落盘 + 原子写（temp + rename）+ 启动恢复」，配合 Electron 的 `crashReporter`（Crashpad，minidump 默认存于用户数据目录 `Crashpad/`，可 `app.setPath('crashDumps', ...)` 重定向）与渲染进程崩溃后重启续写。注意一个真实教训：**原子写 + 写队列仍可能丢数据**——当「读索引 → 改 → 写」是复合事务时，两次操作可能都读到旧快照，各自写入都成功、最后一次覆盖前者，表现为「无异常、无报错、数据消失」。因此 read-modify-write 必须作为一个串行事务处理。
8. **离线能力矩阵**。docs/01 §7 要求「全程不联网也能完成除 AI 调用外的所有步骤」。把功能按网络依赖分三层：**纯本地**（写作、编辑、大纲、设定卡、校验、统计、导出、索引重建）、**本地优先可选云**（云备份 WebDAV/S3/Syncthing，密钥本地持有）、**离线降级**（AI 副驾：本地模型 Ollama/llama.cpp 可离线，云端模型需网络且必须优雅失败）。

## 3. 可转化为产品规则的关键实践

1. 渲染层不直连文件系统 → 所有 fs 操作经 preload 暴露的受限 API 进主进程，符合 context isolation 安全模型。
2. IPC 契约「一消息一方法」→ 禁止透传 `ipcRenderer`，参数需可序列化，清单见 §5。
3. 主进程独占写、渲染层只读 → 索引库写操作只在主进程；渲染层查询走只读连接或 IPC 请求。
4. SQLite 开 WAL + 只存索引 → `PRAGMA journal_mode=WAL`，索引库位于 `.yushu/`，**排除于网盘/Git 同步目录**。
5. 原子写文件 → 统一「写临时文件 → fsync → rename」，避免半写坏文件。
6. chokidar 监听项目 → 启用 `atomic` 与 `awaitWriteFinish`；对自身写入加「忽略窗口」，避免自触发回环。
7. 外部修改冲突三方合并 → 以「磁盘最新内容 / 内存未保存内容 / 上次已保存基线」做合并，冲突时生成旁路文件并提示，绝不静默覆盖。
8. 防丢稿四层防线 → 见 §5 参数；崩溃后启动即检测未保存状态并恢复。
9. 崩溃可观测 → 集成 crashReporter（本地留存或可选上报），记录崩溃时的未保存编辑数。
10. 离线矩阵验收 → CI/自测清单：断网后可完成「新建项目 → 建卡 → 写章 → 校验 → 导出 TXT」，仅 AI 相关功能降级。

## 5. 对御书设计的启示

**IPC 契约清单（草案）**

```yaml
# preload 暴露白名单：一消息一方法，禁止透传 ipcRenderer
ipc_contract:
  project:
    - { method: openProject,  channel: "project:open",   args: [path],        returns: ProjectMeta }
    - { method: closeProject, channel: "project:close",  args: [] }
    - { method: listTree,     channel: "project:tree",   args: [],            returns: TreeNode[] }
  doc:
    - { method: readDoc,      channel: "doc:read",       args: [relPath],     returns: { text, hash } }
    - { method: writeDoc,     channel: "doc:write",      args: [relPath, text, baseHash], returns: WriteResult }
    - { method: renamePath,   channel: "doc:rename",     args: [from, to] }
    - { method: watchChanges, channel: "doc:changed",    args: [],  stream: true }  # 主→渲染推送
  index:
    - { method: query,        channel: "index:query",    args: [query, scope], returns: Row[] }  # 只读
    - { method: rebuildIndex, channel: "index:rebuild",  args: [],            returns: { count } }
  app:
    - { method: getConfig,    channel: "app:config",     args: [],            returns: ProjectConfig }
    - { method: crashInfo,    channel: "app:crashInfo",  args: [],            returns: CrashReport | null }
# 规则：渲染层永不 import fs/path；所有写操作携带 baseHash 以做并发冲突检测
```

**自动保存与防丢稿四层防线（参数草案）**

```yaml
autosave:
  layer1_in_memory:            # ① 内存脏标记 + 防抖落盘
    dirty_flag: true           # 任一事务置脏
    debounce_ms: 800           # 打字停顿 0.8s 触发
    max_idle_ms: 5000          # 高频输入下强制落盘上限
  layer2_atomic_write:         # ② 原子写，防半写
    write: "tmp → fsync → rename"
  layer3_snapshot:             # ③ 本地快照兜底
    interval_ms: 60000         # 每分钟一份轻量快照
    keep: 20                   # 环形保留
    dir: ".yushu/backups/"
  layer4_crash_recovery:       # ④ 启动恢复
    on_startup: "扫描未保存/未提交快照 → 弹窗恢复"
    crash_reporter: local-first（默认不上报，可开关）
write_conflict:
  detect_by: baseHash          # 写前比对文件 hash
  on_mismatch: "三方合并 → 失败则写 ch-012.conflict-<ts>.md 并提示"
```

**离线能力矩阵**

```yaml
offline_matrix:
  pure_local: [新建项目, 起源工作台, 设定卡, 大纲, 正文编辑, 一致性校验,
               码字统计, 敏感词自查, 索引重建, 导出 TXT/DOCX/PDF]
  local_first_optional_cloud: [云备份 WebDAV/S3/Syncthing]   # 密钥本地持有

```

**功能建议**

- 文件网关（FileGateway）：唯一 fs 出口，渲染层只调 `window.yushu.*`；支持「裸机模式」降级为只读浏览。
- 外部改动提示条：chokidar 捕获外部修改后在编辑区顶部提示「磁盘版本已变化」，提供 diff 与「采用磁盘版本 / 保留我的修改 / 并存」三选项。
- 忽略窗口：应用自身写入的 500ms 内忽略对应文件事件，避免监听回环。
- 崩溃恢复向导：启动时若检测到未保存状态，列出可恢复的快照与时间点，一键恢复。
- 索引可重建的可见化：设置页展示「索引来源文件数 / 索引可重建状态」，并提供一键重建。
- 离线提示统一：AI 功能在断网时显示「离线不可用，可切换本地模型」，其余功能不弹任何联网阻塞。

**校验规则建议**

- `ipc-renderer-exposed`：preload 白名单外暴露 `ipcRenderer` 或原始通道 → error（安全）。
- `index-in-sync-dir`：`.yushu/index.db` 位于网盘/同步目录或其子目录 → error（WAL 不兼容网络文件系统）。
- `write-without-basehash`：写文件未携带 `baseHash` → error（无法检测并发覆盖）。
- `autosave-debounce-out-of-range`：`debounce_ms` 不在 300–2000ms → warn（太频繁伤盘、太慢丢稿）。
- `unmerged-external-change`：检测到外部修改且无合并/提示记录 → error，禁止静默覆盖。
- `crash-dump-not-redirected`：启用了崩溃恢复但未重定向 crashDumps 到项目可控目录 → info。
- `offline-gate-violation`：非 AI 功能在离线状态抛出网络错误 → error（违 docs/01 §7 验收基线）。

**AI 提示词建议**

- 「冲突合并助手」：给定基线/磁盘/内存三方文本，输出合并后正文与冲突摘要，供用户确认。
- 「离线可用性自查」：对新增功能生成「是否需要网络」的判定与降级方案建议。
