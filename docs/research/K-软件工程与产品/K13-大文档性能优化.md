# K13-大文档性能优化

> 类别：K-软件工程与产品 ｜ 世界构建金字塔层级：工程层 · 软件工程
> 质量要求：信息来源 ≥6 条、覆盖 ≥3 种来源类型；URL 必须来自真实检索结果。

## 1. 领域定义

研究"百万字项目在普通机器上依然流畅"的工程手段：启动预算、内存预算、编辑延迟、索引/检索耗时、后台计算调度与性能回归门禁。边界划分：K09（全文检索）与 J04（RAG）各自给出功能级性能预算，本领域提供统一的预算表与调度/优化方法论；K02 研究编辑器交互与大文档加载策略，本领域给出进程/线程与内存视角的约束；docs/01 §7 的性能隐含要求（离线可用、导入即时）是验收来源。核心问题：Electron 多进程如何把重计算挪出主线程；编辑器如何只渲染视窗内内容；SQLite 查询如何避免全表扫描与深分页；性能如何被基准脚本与 CI 门槛守住。

## 2. 核心知识框架

1. **性能预算先行**。Electron 官方强调"Measure, Measure, Measure"：先剖析最耗资源的部分再优化，且性能是开发者责任而非框架保证。对御书需把"启动到可写作""打开百万字项目""输入到上屏（编辑延迟）""章节保存到索引可见""单次检索 P95""常驻内存上限"写成可测预算（对齐 docs/01 §7 与交接文档要求），并区分冷/热启动、空库/满库。
2. **进程与线程模型**。Electron 有 main（浏览器进程，含 UI 线程）、renderer（每窗口）、utility 三类进程；主进程与渲染进程都不得被长任务阻塞（阻塞 UI 线程等于整个应用冻结）。重计算（分章、实体抽取、索引构建、全文统计、导出打包）应移至 `utilityProcess.fork`（等价 `child_process.fork`，走 Chromium Services API）或 Web Worker/worker_threads；渲染侧可用 Web Worker（无 DOM、`postMessage` 走结构化克隆，大对象用 transferable 免拷贝，>50ms 的同步任务即有掉帧风险）。
3. **编辑器大文档策略**。单章通常数千字，但"全库视图/大纲/关系表"可能面对十万级条目：列表类 UI 用虚拟滚动（只挂载视窗内节点），长文本用分片/按需测量，避免一次性解析整卷 Markdown；编辑器内部状态变更走事务式更新（K02 的 CodeMirror 6/ProseMirror 模型天然支持增量）。
4. **数据库查询优化**。SQLite 查询计划器依赖索引：无索引 = 全表扫描（SCAN），有可用索引 = SEARCH；多列索引按前缀生效；"覆盖索引"含查询所需全部列则无需回表，计划中显示 `USING COVERING INDEX`；排序若无法借索引会出现 `USE TEMP B-TREE FOR ORDER BY`。统计信息需 `ANALYZE` 维护。分页用游标（rowid/keyset）而非大 OFFSET，避免深翻页退化。
5. **内存预算与泄漏排查**。Electron 基础内存来自 Chromium/Node 与依赖；常见陷阱是"粗心引入模块"（`require` 即拉入庞大依赖链）与"过早加载代码"。排查靠 DevTools 内存快照 + 多进程 Chrome Tracing，关注常驻对象（缓存、索引句柄、未摘除的事件监听、未 terminate 的 Worker）。
6. **启动优化**。策略包括：懒加载非首屏模块、按用户路径延后非关键任务、剥离无用 polyfill、打包与 tree-shaking、无默认菜单时调用 `Menu.setApplicationMenu(null)`、预热 SQLite 连接与热索引、避免启动即全量索引。
7. **性能回归测试**。建立固定负载（合成百万字项目 + 真实样本）与脚本化指标采集，纳入 CI 门槛；在真实机器与低配机器各跑一轮，观察趋势而非单点。

## 3. 可转化为产品规则的关键实践

1. 性能预算表进仓库 → `perf-budget.yaml` 定义启动/内存/编辑延迟/索引/检索阈值，测试与 CI 共用。
2. 重计算一律出主进程 → 分章、抽取、索引、统计、导出走 `utilityProcess`，渲染侧长任务走 Worker。
3. Worker 大对象用 transferable → 避免结构化克隆的拷贝开销。
4. 列表虚拟化 + 长文本分片 → 全库列表/大纲/关系表虚拟滚动；编辑器按视窗渲染。
5. 索引覆盖查询 → 为高频列表查询建覆盖索引；用 `EXPLAIN QUERY PLAN` 校验"SEARCH / COVERING INDEX"，禁用深 OFFSET 分页。
6. 定期 `ANALYZE` 与 `optimize` → 维护统计信息与 FTS 段合并，防止查询随时间退化。
7. 启动懒加载与预热 → 首屏只加载写作所需；连接与热索引预热，其余延后。
8. 依赖体量与模块加载审查 → 新增依赖前评估体积与 `require` 代价，避免启动路径引入重模块。
9. 内存基线守卫 → 空闲常驻内存设上限；快照对比纳入发布检查；Worker/监听器生命周期纳入 code review 清单。
10. 性能回归 CI 门槛 → 基准脚本超预算即失败，输出趋势报告（与 K09 检索基准共用脚本）。

## 5. 对御书设计的启示

**数据结构建议：性能预算表（`perf-budget.yaml`）**

```yaml
# 与 K09/J04 共用同一份预算；数值为初始目标，实测后回填
budgets:
  startup:      {cold_to_editable_ms: 2000, hot_to_editable_ms: 800}
  project_open: {million_chars_ms: 3000}      # 打开百万字项目到可滚动
  edit:         {keystroke_p95_ms: 16, save_to_indexed_ms: 500}   # 上屏≈1 帧；保存→可检索(K09)
  search:       {query_p95_ms: 80, rebuild_cpm: 20000}            # 重建吞吐下限 字/分钟
  memory:       {idle_rss_mb: 600, million_chars_rss_mb: 1200}
fixtures:
  - synth-1m            # 合成百万字项目（分章/设定齐全）
  - real-sample-300k    # 真实样本
runners: [ci-low-spec, ci-mid-spec, local-dev]
```

**重计算调度（出主进程）**
```text
main (窗口/生命周期，仅短任务)
  ├─ renderer (编辑器 UI，仅交互与渲染)
  │     └─ Web Worker：软换行重排、字数统计、局部 diff
  └─ utilityProcess "engine" (Node.js)
        ├─ 分章 / 实体抽取 / 索引构建（K09、J04）
        ├─ 导出打包（EPUB/DOCX/PDF）
        └─ 全文统计 / 一致性校验（J07）
```

**查询优化示例（避免全表扫描与深分页）**
```sql
-- 覆盖索引：列表页只取 id+标题+字数，不回表
CREATE INDEX idx_chapters_list ON chapters(volume, idx, id, title, word_count);
EXPLAIN QUERY PLAN SELECT id, title, word_count FROM chapters
WHERE volume=? ORDER BY idx;   -- 期望：SEARCH ... USING COVERING INDEX

-- 游标分页（keyset）替代 OFFSET
SELECT id, title FROM chapters WHERE (volume, idx) > (?, ?) ORDER BY volume, idx LIMIT 50;
```

**校验规则建议**
- `perf-budget-exceeded`：任一指标超 `perf-budget.yaml` → error（CI 门槛）。
- `perf-short-task-on-main`：构建期静态检查主进程/渲染路径出现同步重计算（无 Worker/utilityProcess 包裹） → warn。
- `db-plan-regression`：关键查询 `EXPLAIN QUERY PLAN` 由 SEARCH/COVERING 退化为 SCAN → error（查询计划基线快照）。
- `db-deep-offset-page`：列表查询使用 `OFFSET > 1000` → warn，改用游标分页。
- `worker-leak`：Worker/utilityProcess 未在销毁时 terminate/退出 → error（内存泄漏红线）。
- `startup-eager-load`：启动路径 import 了标记为重模块的白名单外依赖 → warn。

**功能建议**
- 性能自检面板：一键跑基线脚本，展示六项指标与预算差值（与 K12 安全自检共用面板）。
- 索引重建后台化：utilityProcess 执行，带进度与可取消，UI 全程可用。
- 大项目打开进度：先渲染目录与最近章节，正文与设定按需加载（渐进可用）。
- 内存监控（开发者模式）：显示各进程 RSS、Worker 数量、索引句柄，异常增长提示抓取快照。

**AI 提示词建议**
- 「性能归因」：给定基准脚本输出（各阶段耗时/内存），输出 top-3 瓶颈假设与验证步骤（如"索引构建占用超标 → 检查是否误在渲染进程执行"）。
- 「查询计划解读」：给定 `EXPLAIN QUERY PLAN` 输出，判断是否退化为 SCAN/临时 B-Tree 并给出索引建议。
