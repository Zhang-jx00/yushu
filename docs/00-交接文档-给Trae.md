## 1. 项目最高纲领

### 1.1 宗旨

> **从起源构建世界。**
>
> 每一部小说都不单单是一篇文字，而是要创作出另一个世界：文化完整，有历史，有生态，有人文，有地理的完整世界。

这不是宣传语，而是产品的最高设计约束：

- 一部作品不是一堆章节文件，而是一个完整的 `World`，章节只是这个世界中的叙事切面。
- 世界应当能够从起源、法则、地理、生态、历史、文明、社会一直推演到人物和故事。
- 修改上游设定时，工具必须能指出下游受到的影响。
- AI 只能作为副驾，不能取代作者的创作主导权。

### 1.2 四条不可违背的设计原则

1. **项目即世界**：一个项目包含世界本体、世界中的故事、人物、地点、势力、事件、伏笔和章节。
2. **自上而下推演**：起源 → 法则 → 地理 → 生态 → 历史 → 文明 → 社会现状 → 人物 → 故事。
3. **流派可组合而非单选**：频道、世界、手法、基调四个维度可以多选、融合、修改和自定义。
4. **一致性是生命线**：战力、历史、时间线、称呼、人物声线、规则和伏笔都要有结构化约束与检查机制。

## 2. 已确认的产品决策

这些决策已经由用户确认，后续不要擅自改回其他方向。

### 2.1 产品定位

「御书」是一个：

- 中文网文作者优先的开源小说创作工具。
- 支持玄幻、仙侠、西幻、科幻、中式恐怖、西式恐怖、都市、甜宠、穿越、异世界、系统文、男频、女频、纯爱、百合、无 CP 等各种流派。
- 允许用户选择多个流派并融合。
- 允许用户修改自动生成的派系配置。
- 允许用户从零创建自己的派系。
- 允许派系包和插件被导出、导入和社区分享。
- 以本地数据主权、世界观管理、AI 辅助和长篇一致性为差异化核心。

### 2.2 技术基线

目前规划基线如下：

- 桌面端：**Electron**，但核心引擎必须与 Electron 解耦，保留未来评估 Tauri 的可能。
- 前端：React + TypeScript。
- 正文编辑器：TipTap / ProseMirror。
- 源码或 Markdown 模式：CodeMirror 6。
- 正文和设定卡：Markdown + YAML frontmatter，文件是用户可读的真源。
- 项目配置：TOML 或等价的稳定配置格式。
- SQLite：只做全文索引、关系查询和缓存，不作为唯一数据真源。
- 中文全文检索：SQLite FTS5 + 中文分词扩展（优先评估 `wangfenjin/simple`）。
- 向量检索：优先评估 sqlite-vec + 中文 embedding；必须保留替代方案。
- LLM 接入：以 OpenAI Chat Completions 兼容协议为主干，厂商通过 Provider 描述接入。
- 本地模型：Ollama、llama.cpp、LM Studio、vLLM 均应能作为 OpenAI 兼容端点接入。
- 导出：Pandoc → TXT / EPUB 3.3 / DOCX / PDF；EPUB 使用 EPUBCheck 做质量门禁。
- 关系图谱：中等规模优先 SQLite `nodes` / `edges` 表；展示层可用 React Flow、G6 或 Sigma.js。

### 2.3 数据主权承诺

- Markdown 正文和设定卡可脱离御书直接读取。
- SQLite 索引随时可以从 Markdown 文件重建。
- API Key 本地加密保存，不上传到御书服务器。
- 不强制云端账号。
- 云备份只作为可选能力，候选后端包括 WebDAV、S3 兼容存储和 Syncthing。
- AI 功能默认可关闭，并记录 AI 使用证据、编辑轨迹和版本历史。

## 5. 已形成的核心产品模型

### 5.1 世界引擎层级

推荐保持如下依赖顺序：

```text
World
└── Genesis / 起源
    └── Laws / 法则
        ├── Geography / 地理
        │   ├── Climate / 气候
        │   ├── Resources / 资源
        │   └── Locations / 地点
        ├── Ecology / 生态
        │   ├── Species / 物种
        │   └── Food Web / 食物网
        ├── Eras / 纪元与历史
        │   └── Civilizations / 文明
        │       ├── Cultures / 文化
        │       ├── Religions / 宗教
        │       ├── Governments / 政体
        │       └── Economies / 经济
        ├── Factions / 势力
        ├── Characters / 人物
        ├── Events / 事件
        ├── Storylines / 故事线
        └── Chapters / 章节
```

这不是强制每部作品填满的表单。必须支持：

- 现实都市只填写必要的人文、商业和社会字段。
- 玄幻作品深入填写起源、法则、地理、生态、纪元、境界和战力。
- 恐怖作品重点填写禁忌、规则、诡异档案、信息可见性和线索。
- 用户能够隐藏、不启用或自定义任意层。

## 9. 交接时必须注意的事实与风险

### 9.1 不要误判“研究资料数量”

412 份是预研种子库数量，不等于最终 125 个领域的规范化来源总数。最终计划要求每个领域至少 6 条来源，因此理论最低值是：

```text
125 × 6 = 750 条领域级来源
```

后续应统计每个领域实际引用了多少条，而不是只在总 README 写“已有 412 份”。

### 9.2 不要把派系做成单选下拉框

必须支持：

- 多维多选。
- 同一维度多选。
- 包之间冲突提示。
- 用户手动覆盖派系规则。
- 用户新建派系。
- 派系包版本化。
- 派系包导入导出。

### 9.3 不要把世界模型做成强制巨型表单

不同作品需要的世界层级不同。要采用：

- 少量必填字段。
- 渐进披露。
- 流派包按需启用字段。
- 用户可跳过、隐藏和稍后补充。
- top-down 与 bottom-up 混合。

### 9.4 不要让 AI 直接覆盖正文或设定

任何 AI 结果都应：

- 以候选形式呈现。
- 支持 diff。
- 支持整段或局部采纳。
- 记录来源和 AI 使用记录。
- 在用户确认后写入真源。
- 可以撤销和恢复。

### 9.5 不要把 SQLite 当唯一真源

Markdown/YAML 文件必须可独立读取、版本化和迁移。SQLite 索引损坏或被删除时，必须能够重建。

### 9.6 不要未经验证地宣称平台规则永久有效

起点、番茄、晋江、飞卢的审核、全勤和 AI 政策会变化。平台规则应设计成外置、带来源、带生效日期和版本号的规则包。
