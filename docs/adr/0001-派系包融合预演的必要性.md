# ADR-0001：派系包融合必须经过「融合预演」才落库

- 状态：已采纳（M1）
- 日期：2026-09-29
- 关联：docs/03 §8.3、docs/04 §4.3（T1-4）、G06 派系包建模、docs/01 §3.1

## 背景

派系不是单选：用户可以在频道 × 世界 × 手法 × 基调四个维度上多选，并把多个派系包叠加使用（例如「玄幻 + 系统流」与后续的「凡人流」兼容包）。多个包会同时提供同名件套（world_preset、schema 扩展、规则、大纲模板等），彼此的取值可能：

- **新增**：只在一个包里出现的件套/条目；
- **覆盖**：同名条目被多个包提供，需要仲裁胜者；
- **冲突**：包间存在语义互斥（如「无女主」× 纯爱甜宠的 `romance_mode_default` 不一致，或 `fusions.conflicts_with` 显式声明）。

如果把融合结果直接写进 `project.toml` 与 `world/world.yaml`，用户就看不到自己到底选了"什么组合"，后续世界构建会在未知设定上展开，冲突也只能在写小说时才发现——而"一致性是生命线"（docs/03 §1.1）。

## 决策

`fuse(packs[])` 产出**融合预演报告**（新增 / 覆盖 / 冲突三类 + 融合后的四维并集），由用户在新建向导中确认：

1. 报告在画面上完整呈现仲裁结果（覆盖项的胜者、冲突项的原因、四维并集）；
2. **存在 error 级冲突时拒绝落库**（`E_FUSION_NOT_READY`），必须先移除冲突包或调整选择；
3. 确认后的冲突记录（含 severity）一并写入 `project.toml`，作为项目级留档；
4. 覆盖仲裁规则保持确定性（后加载包胜出），禁止依赖文件系统顺序的隐式行为。

## 后果

- **正向**：世界真源带着"融合来源与仲裁记录"出生；后续 M5「派系包工坊」的即时 lint 与"导出前自检"可复用同一报告结构；派系包作者能通过 `fusions.compatible_with / conflicts_with` 显式表达意图。
- **成本**：新建项目多一步确认；`project.toml` 增加 `[genre.conflicts]` 记录。
- **边界**：M1 的仲裁只到"件套/条目"粒度（占位规则不参与求值），细粒度规则求值在 M4 的规则 DSL 沙箱中完成。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 直接融合、不预演 | 用户无法感知冲突，问题推迟到写作时才暴露（已否决） |
| 只允许单选派系 | 违背 docs/01 §3.1「派系不做单选」红线（已否决） |
| 冲突一律阻断 | 兼容包之间的大量重叠属正常覆盖，一律阻断会让多选不可用（改为仅 error 级阻断） |
